# 决策：[069-D1] 学习把理解记成原话转述，同一件事的认识只堆不推进

Status: proposed
observed_in_version: 0.7.0 第 3 次预览（测试版，049 从第 30 轮起回放）
fixed_in: pending
user_verified: pending

## 来源

Murphy 原话：起草决策

起因是开发者反馈 F29：理解是在 human loop 中，人已有的和正在形成的、与目标相关的认知；Arcfold 最终要建立一个完整的、不断发展的、多层次的、对这件事的认知。F29 附件里的那段注释给了可检验的样子：下次讨论产品设计时，Arcfold 能自己讲出当初那句话为什么写偏、后来补上了哪一层、今天会怎样影响手上的决定。

相关反馈：F22（目标、方法、理解的内容怎么分工）、F46（学习只有当场、没有事后整理）。事后整理的时机由 053 处理，子目标认识提到上级由 067 处理，本决策都不碰。

源码按 GitHub main@5f6a261 核对。测试版用的学习提示词 `arcfold.tree.learning/6.0.0` 与 main 相同。

## 问题

每轮学习写下的理解，几乎都是"用户认为、用户希望……"的原话转述，没有写成围绕目标的认识。同一件事的认识往前推进时，只能另起一条新条目，原来那条不会被推进。时间一长，同一件事攒下一串并列的句子，看不出哪条是在哪条基础上发展出来的。

### 实际例子

数据来自测试版第 30 轮起回放的目标树（只读查看 `tree.sqlite`）。

- 一共 62 条理解：57 条来自每轮学习，5 条来自离开目标时的整理。54 条标为用户亲口表达，几乎都以"用户……"开头。
- 原会话 11-19 07:39 那轮，开发者指出用"对用户的理解"概括 Arcfold 是偏的。学习记下的是"用户不希望用'对用户的理解'概括 Arcfold，因为他认为用户理解、长期记忆类项目已经很多，这种表述缺乏新意"。这把它记成了措辞偏好。F29 附件说的是：这句纠正改变了"Arcfold 需要理解什么"这个产品判断。
- 第 53 轮和第 54 轮，开发者把"认知的递进"推进了一层，从"过去形成的判断持续影响未来"推进到"总有更新的过去影响未来"。学习记成两条并列的新理解，没有一条说明后一条是在前一条上推进的。
- 62 条里只有 4 条有第二版，原因都是程序替换来源包，内容上一条都没被推进过。另有 1 条标为已变、1 条标为无效，都是开发者明确纠正的。
- 第 39 轮，助手把两个案例连起来，得出"已经形成的整体认识，没有持续成为局部决策的依据"。开发者下一轮说"那我们可以开始写作了吧"，初稿也沿用了这句。第 39、40 轮的学习都没有记这句话，只记了"用户认为开发工具应服务于效率"等三条偏好。

### 原因

都有代码可查（main@5f6a261）。

1. 提示词把理解引向"关于用户"。判断标准列出的常见内容是：用户想要什么、轻重取舍、看法及其变化、处境和条件、关于用户自己、分工（`src/tree/prompts.mjs:521`）。唯一的正面例子是"用户把数字准确看得比速度重要"（`src/tree/prompts.mjs:527`）。模型就照这个句式写。来源本来已经有单独的 source 字段，主对话也能看到（`src/tree/context.mjs:99`），句子开头的"用户认为"是重复的。
2. 合作中一起得出的判断没有地方放。提示词的"不记"里有"助手给用户的建议"（`src/tree/prompts.mjs:522`），却没说用户接着用了的判断算什么。第 39 轮那句就是这样漏掉的。
3. 推进已有认识没有可用的动作。学习只能新增，或者用 changes 改旧条目。changes 只在"用户明确纠正已有理解或改变了看法"时用，还要逐字引用本轮用户原话（`src/tree/prompts.mjs:524`、`src/tree/prompts.mjs:173`）。补一层、补原因、收窄范围都不算纠正，只能另起一条。

## 方案

1. 改判断标准和例子。理解的核心是当前目标：要把这个目标做好，现在对相关的事怎么判断。涉及的对象可以是产品、文章、计划，也可以是用户本人，但对这些对象的理解，都是为了怎样做好这个目标。content 里不再写"用户认为""用户希望"，谁说的由 source 字段表达。删掉"用户把数字准确看得比速度重要"这个例子，换成两个：一个是用户自己说出的判断，一个是合作中得出、用户接着用了的判断（用第 39 轮这类情况，去掉个人内容）。
2. 写明三种来源都要记：用户说出的；事情经过和结果里显出来的；双方讨论中一起想清楚的。助手提出、用户在本轮或下一轮接着用了的判断，source 写 assistant_inferred，sourceIds 引用用户接着用的那句。"不记"清单保留进度、一次性任务内容和一般知识，把"助手给用户的建议"改成"用户没有接受或没有用上的助手建议"。
3. 新增"推进"动作（develop）。如果本轮内容在 knownItems 里某条理解的基础上补了一层、补了原因或收窄了范围，就推进那一条，不新建：
   - 写成同一条目的新版本，沿用现有 rewrite 的版本机制，版本号加 1，来源累积，旧版本保留（`src/tree/items.mjs:249`、`src/tree/items.mjs:256`）。
   - 每次推进要写一句 basis，说明本轮是什么推动了变化。sourceIds 要含本轮来源，但不要求逐字引用。
   - 只能推进理解，不能推进方法；受用户保护的条目不能推进；同一条目同一轮不能既 change 又 develop。每轮最多推进 2 条。
   - 用户明确纠正仍然走现有 changes（changed／invalid），规则不变。
4. 主对话和学习看到被推进过的理解时，除了当前内容，再带上一版的一句话和这次推进的 basis。只带上一版，不带全部历史。这样主助手能说出"之前怎么判断、这一轮补了什么"。

不改的部分：每轮最多 3 条新理解的上限、方法的生成规则、整理的时机和回看（053）、提升到上级（067）、目标归属判断。

## 预期效果

- 新写的理解读起来是为做好当前目标而形成的判断，不再以"用户认为"开头；来源照样看得出。
- 像第 53、54 轮那样的推进，落到同一条理解的第 2 版，保留第 1 版和推进依据。
- 像第 39 轮那样，合作中得出、用户接着用了的判断能被记下。
- 同一件事的理解条数增长变慢，因为一部分新增变成了推进。
- 学习的模型调用次数不变；推进过的条目在输入里多一句上一版，输入略长。

## 考虑过的其他做法

- 只改提示词的标准和例子，不加推进动作。放弃原因：主语能改过来，但第 53、54 轮那种变化还是只能新建一条，同一件事照样越堆越多。
- 放宽现有 changes，不再要求逐字引用。放弃原因：changes 会把旧条目标成已变或无效，再生成新条目，以后分不清是推进还是推翻；而且"纠正要有用户原话"是保护用户的规则，不该为这个放松。
- 让学习每轮读更长的历史，自己发现认识怎么发展。放弃原因：输入变长、费用增加；有了推进动作和已有条目，就能接住跨轮的发展。
- 学习时直接把认识挂到它真正回答的上级目标。放弃原因：这是另一个问题（挂在哪里、谁能看见），067 在离开时提升，学习时就近挂载另议，一份决策只写一个问题。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

- 测试：develop 指向 knownItems 中一条有效理解，结果是同一条目版本加 1，旧版本保留，来源累积，basis 保存。
- 测试：develop 指向方法、受用户保护的条目、不在 knownItems 里的条目，或 sourceIds 里没有本轮来源，这一项被拒绝，同批其他项照常保存。
- 测试：同一条目同一轮同时出现 change 和 develop，被拒绝。
- 测试：主对话背景里，被推进过的理解带上一版的一句话和 basis；没推进过的不带。
- 测试：现有 changes 的行为和校验不变。
- 测试：学习提示词里不再有"用户把数字准确看得比速度重要"这个例子；新例子和"不记"清单按方案第 1、2 条写入。
- 回放观察（不作为发布条件，单独记录）：用 049 同一检查点，从第 30 轮起重放同样的用户输入，前后对比四项：以"用户……"开头的理解占多少；推进了多少条；第 53、54 轮是否落到同一条；第 39 轮那句判断是否被记下。

## 风险

- 模型可能把不相关的新认识硬推进到旧条目上。旧版本保留、basis 必填，可以回查；之后检验也能改写或撤回。
- 去掉"用户认为"以后，光看句子分不出是用户说的还是助手推断的。主对话已经有 source 字段；开工时核对 Arcfold 页面是否显示来源，不显示就另开任务补上，不在本任务里改界面。
- 推进让输入变长：每条上一版最多 300 字，只带一版，影响小。
- 本决策不解决认识挂在兄弟目标下、当前目标看不见的问题（回放里"每日待办"下的 28 条，在"第一篇"里都看不到，`src/tree/context.mjs:113`）。那由 067 和后续挂载的任务处理。
