# 决策：[025-D3] 学习请求超出上下文后目标树学习永久停住

Status: proposed
observed_in_version: 0.5.4
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F15（2026-11-18T10:38:40+00:00 登记）

## 问题

日常 DSH 0.5.4 里，从 2026-11-18 08:58Z 起，目标树的学习不再进行，目标概述和学习内容都不更新，之后每轮对话产生的学习任务一直排队。

实际经过（证据在日常资料 `~/.dsh/arcfold-desktop/tree.sqlite` 和学习会话 `session-0d23cea1` 的原生记录）：

1. 08:58 旧学习会话预计输入 713749，超过 700000，按设计暂停学习、整理摘要，开了第二个学习会话。
2. 新会话的第一条输入仍有约 2.9 MB：`epochSeed.recent` 保留的最近三轮学习输入约 1.5 MB，本轮 `sources` 约 1.2 MB，两部分大多是长工具输出（单条最大约 10 万字符）。本地估算没有拦下。
3. 服务直接拒绝：`turn/end` 为 error，`CONTEXT_WINDOW_EXCEEDED`，没有任何模型输出，用量为 0。
4. 因为请求身份已经登记过，`model-owner.mjs` 把这个任务记成 `unknown`（RESULT_UNKNOWN），而不是 `failed`。
5. `jobs.mjs` 在同一节点有 `unknown` 学习任务时拒绝准备任何后续学习或整理任务（LEARNING_UNKNOWN）。启动时的 `recover()` 每次读到的还是同一份记录，结果仍是 `unknown`，所以重启也解不开。之后三轮对话的学习任务（2b99416e、8155ab82、c50b7e03）一直 queued。

## 方案

1. 服务明确拒绝、没有产生任何输出时，按已知失败记录。条件同时满足：原生记录里本任务那一轮以 error 结束，中间没有 assistant 输出，错误码是上下文超限，且每个请求的原生请求记录都是已结束的失败（`failed`）。这时把任务记为 `failed`（错误码和原文保留服务返回的内容），请求记录不改。超时、流式中断、写盘失败等真不知道结果的情况不变，仍记 `unknown`。只处理原生模型路线（日常 DSH 用的就是这条）；计量路线的记账规则不动。
2. 学习任务因上下文超限失败后，这一轮的学习改到新的原生学习会话里重新冻结、重新发送，原文保留。因为旧会话里已经留着那条被拒的超长输入，接着用旧会话还会超限。具体分两种：
   - 有比"最近三轮"更早、还没整理过的学习记录：和 LEARNING_PRESSURE 一样，暂停、整理，整理成功后进入新会话。
   - 没有可以再整理的内容（本次实际情况：刚整理完、新会话的第一条就被拒）：不暂停，直接沿用当前已核对的摘要和最近三轮，开一个新会话。
3. 新学习会话的起始材料要真的变小。`learningSeed` 保留最近三轮时，用户和助手原话照原文保留，长工具输出只保留来源引用、哈希和长度，不放原文。本轮 `sources` 里的长工具输出同样处理。阈值在实现时按现有估算器定，并写进测试。
4. 已经卡住的日常资料不用手工改：更新后启动时 `recover()` 重新读那条学习记录，按第 1 条改记为 `failed`，排队的学习任务按原顺序继续。

## 预期效果

再遇到学习输入超限时，学习会暂停、整理，然后继续，不会永久停住。Murphy 更新后，现有卡住的三轮学习会自动补上，目标概述和学习内容恢复更新。

## 考虑过的其他做法

- 只做第 1、2 条，不缩小起始材料：整理后新会话还是一样大，会反复超限、反复整理，学习还是停着。
- 把 `unknown` 学习任务过一段时间自动放行：可能重发一个其实已经被处理的请求，重复计费，违反"结果未知不重发"的规则。
- 把本地估算调保守：只能更早拦下，起始材料本身太大的问题还在。可以以后单独调。
- 把第 3 条拆成单独的决策：拆开后单独上线第 1、2 条无法让学习恢复，所以放在同一个问题里。
- 第 2 条一律走"暂停、整理"（D1 的写法）：本次实际情况里没有更早的内容可整理，会落到"无法整理"，学习继续暂停，问题没解决。所以在 D2 改为上面两种情况。
- 被拒后继续用旧会话：旧会话里那条被拒的超长输入还在，下一次请求照样超限。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：standard 对比未安装 Arcfold 的原版完整工具清单；arcfold-main 核对 bash、read、write、edit、glob、grep。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。
- 模拟服务对学习请求返回上下文超限、无输出：该任务记为 `failed`，不是 `unknown`；有更早内容时该节点排一次整理，整理完成后这一轮在新会话里重新发送，排队的学习任务依次运行并提交。
- 刚换完会话、第一条就被拒（没有可再整理的内容）：不暂停，自动换到新会话，这一轮和排队的学习任务依次运行并提交，不需要手工操作。
- 模拟服务在流式输出中途断开或超时：任务仍记 `unknown`，后续学习仍被拦住（不放宽现有保护）。
- 起始材料里有多条 10 万字符以上的工具输出时，新学习会话第一条输入的估算低于上限，原话部分与原文一致。
- 用一份带有本问题形状 `unknown` 学习任务的资料启动：`recover()` 后该任务为 `failed`，排队的学习任务继续，原有记录不丢。

## 风险

- 第 1 条判断条件写宽了，会把真不知道结果的请求当成失败，之后可能重发、重复计费。只认"本轮以 error 结束且没有任何输出"加上下文超限错误码，其他情况一律保持 `unknown`。
- 第 3 条去掉长工具输出原文后，学习模型看不到工具细节，判断可能变粗。学习主要依据用户和助手原话，影响应当有限，验收时对比整理前后的学习回执。
- 本次不处理：01:42 宿主因 "unable to open database file" 崩溃、本地估算偏低、此前 5 次学习都没写出新条目。这些另行确认。
