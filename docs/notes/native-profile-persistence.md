# 决策：修复原生模型启用后配置刷新导致 Arcfold 停止工作

Status: proposed
observed_in_version: 0.5.2
fixed_in: 0.5.3
user_verified: pending

## 来源

0.5.2 隔离验收失败；开发者已指定修复后发布 0.5.3，沿用 248c8b5 入口。

## 问题

根因：启用时只改了当时的运行配置，没有保存到 DSH 下次会读取的配置文件；刷新后 Arcfold 服务消失，首条消息无法发送，界面却仍显示就绪。实际测试资料与原版 DSH 小复现均证实这个保存缺口；截图里的 web boot 导入错误是否同源仍待测试账户确认。

## 方案

改法：通过 DSH 原生配置保存功能写入有明确归属的 Arcfold 运行设置，并让就绪状态对应实际服务。密钥、模型设置和聊天模型列表继续由 DSH 管理。网页导入错误先在测试账户核对；若不同源但改动小，一并修补，若改动大则报告后再定。

新任务和新 PR 按旧入口更新两份包版本、锁文件与 CHANGELOG。修复 PR 审阅累计上限 1 美元，修后再审沿用同一授权；通过即合入。0.5.2 记为验收失败、不发布，草稿和原证据保留；0.5.3 发布完成前不合入 #34、不切换入口。

## 预期效果

首次启用、配置刷新和完全重启后，用户都能继续聊天；主回答及后台调用继承各自来源轮次选择的模型。

## 考虑过的其他做法

不采用反复补写内存配置或让用户手改文件；两者不能保证正常刷新后继续使用。开发者已决定不替换 0.5.2 原候选。

## 验收标准

- 先自动跑本机合成测试：全新安装后首条消息成功、配置刷新后服务仍在、完全退出重启后读回原数据；检查失败和未同意启用时的状态。
- 检查及独立审阅通过后合入，按旧流程双构建并核对许可；最终原包再做普通账户隔离验收，覆盖安装、下载失败恢复、更新、重启及原生模型列表中两种模型的主回答和后台来源一致性。需要人工操作时合并步骤。
- 隔离验收通过后直接发布 GitHub/npm，包与验收对象一致；发布后提供日常 DSH 更新步骤。原失败不得改写为通过。

## 风险

配置保存会触发组件重新加载，需避免启动互相等待、覆盖其他设置或重复调用。网页导入错误尚未解释；若需要大范围改动，先报告再定，不据小复现宣称整包修复。
