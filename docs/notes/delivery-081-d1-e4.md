## 来源

开发者另已明确要求期间新增 PR 一起带上。目前第二次候选之后的产品改动清单是 #82、#83、#84；这次将三项具体范围列清楚，旧候选和失败历史不覆盖。

## 问题

第二次候选包含已知选模及目标面板渲染故障，不能发布。修复源码合入不等于已经制作或验证新的安装包；新增主线改动也不能靠重打包默默带入。

## 方案

采用未发布版本的同版本修补，仍准备 0.8.0。保留候选 2 已有的全部内容（最初十三项以及 #74–#80 七项），在明确的当前主线基础上纳入以下三项：

| PR | 本次新增内容 |
| --- | --- |
| #82 | 主助手切换已有目标时，用本轮当前目标的版本核对请求，修正目的目标版本不同而错误拒绝切换的问题。 |
| #83 | 断线后继续请求时，在请求定稿前刷新已经变化的目标背景，保留原话、轮次、归属和背景校验。 |
| #84 | 补齐选模读回所用原生通信服务声明，避免监听绑定被拒和目标面板渲染中断；回归覆盖真实插件服务访问限制。 |

发行任务仅修改包元数据、锁文件和更新日志，汇总这三份新增更新说明，沿用 0.8.0 原有一句话介绍。已经消费的二十份说明保留在版本历史中，不重复纳入。

走独立发行 PR、GitHub 完整检查、026-A3 已确认的暂停付费审阅规则及受管合入。新候选两份包分别构建两遍并逐字节比较，核对依赖、许可及公开内容；用新原包重新做普通测试账户完整验收。使用本机模拟模型，工程费用 0 美元，真实模型请求为零。

若 main 之后再增加其他产品改动，先停下列出具体差异并重新对齐，不自动收录。

新原包完成后，按两份实际包的校验值另开日常预览安装授权。日常装入新候选、隔离验收及发布前待办全部满足后，再开绑定同一候选与两份包的正式发布授权。本决策不改日常资料、配置或凭据，不迁用旧候选的安装或发布授权。

## 预期效果

新候选保留原 0.8.0 内容并包含上述三项修复；原会话的模型和推理等级选择在页面、持久记录及下一条模拟请求中一致，刷新和重启后保留，目标面板能正常显示。实际回答质量、长期学习效果仍须实际反馈，不能由模拟检查证明。
