## 来源

开发者要求发布 0.8.1。已核对 0.8.0 标签与当前主线，相差已合入的 PR #86–#90；GitHub 与 npm 两份包均未查到 0.8.1。日常目前为 0.8.0 加 #86–#89 的本地覆盖，不是本次待制作的正式包。

## 问题

五项改动已经合入，但尚未进入正式安装包。需要把明确的这五项统一发行，并用实际生成的安装包验证安装、恢复与升级，不把源码检查或本地覆盖当作正式包验收。

## 方案

以头部指定的主线提交制作 0.8.1，保留 0.8.0 全部内容，新增：

- #86：用户明确采用整套做法时保留完整方法，保留短规则和旧格式兼容。
- #87：已明确失败的学习可有限重试，重启保留次数，旧积压补学有总量上限。
- #88：减少历史任务和变更记录的重复读取与解析。
- #89：符合原请求、无回答等条件的断线尝试可继续自动重试，保留失败记录。
- #90：启动恢复与后台扫描期间复用未变化的历史统计，写入、回滚等情况使复用失效。

本交付仅生成版本、锁文件、更新日志和五份更新说明的汇总；不追加功能。后续主线出现范围外产品改动时，先重新确认范围。

按登记入口创建发行 PR、等待自动检查、完成适用的独立审阅并合入。两份安装包分别重复构建并比较，保留原包和验收证据。独立环境使用合成资料和模拟模型，不调用真实模型。审阅沿用现有授权与预算：单次估算不超过 1 美元、同一 PR 累计不超过 3 美元；不另开额度。

原包准备好后，另开绑定本次包的日常预览授权；日常预览、独立验收和下列发布前待办满足后，再开绑定同一候选和两份包的 GitHub/npm 发布授权。当前决策不代替这两次具体授权。

## 预期效果

用户可通过正式更新获得上述五项改动。完整方法保留、明确失败后的有限恢复和历史读取优化进入同一套包；不以模拟验收证明真实模型回答质量或个人数据下的速度提升。

## 考虑过的其他做法

继续使用本地覆盖：不能为正式更新提供一致的包与版本。只发其中几项：与本次确认的五项范围不符，也不能解决剩余已合入改动尚未发行的问题。

## 验收标准

- 两份包均为 0.8.1，源码对应指定主线与发行提交，更新说明恰好覆盖 #86–#90；重复构建的包逐字节一致。
- 本次原包在独立环境完成安装、模拟对话、下载失败恢复、从 0.8.0 更新及退出后重启读回；保留合成会话、目标和学习记录。
- 发布前待办均在本候选原包验证，保存场景和实际结果；未通过或未确认的项目不得写为通过。

## 发布前待办

- 用本候选原包和模拟模型验证完整方法可保存、列出并读回，重启后仍在。
- 用本候选原包和模拟模型验证明确失败的学习及无回答的断线请求按限制恢复，保留失败记录，不无限重试。
- 用本候选原包和合成历史资料验证启动恢复及后台扫描结果一致，修改或回滚后读取新结果，保存耗时。

## 风险

失败后的重试在真实服务中可能再次计费，历史补学也可能产生用量；本交付验收不使用真实模型。日常预览需要退出应用并备份后安装，另行绑定实际包取得授权。独立环境检查不代表个人环境速度已经改善，实际体验仍以开发者观察为准。
