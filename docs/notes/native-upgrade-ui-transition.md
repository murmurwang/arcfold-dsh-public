## 来源

A79 的日常配置差异预检。PR #38 已通过 GitHub 检查，但两份独立资料的真实旧版升级都在启用后的整页刷新失败；没有发送付费审阅、建立标签或发布。原证据保留。

## 问题

根因：设置成功后，Arcfold 立即重新加载整个 DSH 页面；页面请求了正在被替换的界面资源版本。第二次现场记录到旧脚本加载失败，DSH 已开始重新加载组件，但启动检查在恢复完成前弹错；同一旧资源地址返回 404，当前地址返回 200。旧连接停用和运行配置保存已经完成，属于界面切换阶段的另一处问题。历史 F9 只有相同汇总报错，仍不能倒推为已确认同因。

## 方案

改法：沿用 DSH 原生工作区导航，设置完成后只重新初始化 Arcfold 的界面入口，等待它就绪，不强制重新加载整页；失败仍显示错误，不隐藏启动检查。承接 PR #38 的旧连接归属检查、持久保存及回归检查。

继续用 248c8b5 入口、版本 0.5.4。该入口冻结已启动任务的决策和文件范围，不能在 PR #38 加入这次界面修补；建议此新任务承接现有改动，另开 PR 并关闭未合入的 #38，保留其证据。0.5.3 草稿与失败包保留。两份候选都不产生正式发行，直到合入后的完整验收通过。

总修复审阅预算仍不超过 1 美元，PR #35 已用 0.1938501 美元，PR #38 未送审；替代 PR 只使用剩余 0.8061499 美元，修后再审沿用。审阅通过合入，双构建和普通账户验收通过后直接发布 GitHub/npm，#34 和实际入口继续冻结。这些费用和发布安排沿用 A79，不另要一次批准。

## 预期效果

从真实 0.4.1 更新并确认后，可以直接使用原生模型聊天；原会话、目标、模型连接、默认模型和本地插件保留，配置刷新及正常重启后仍能读回。

## 考虑过的其他做法

任意延时不能证明资源已稳定。修改 DSH 本身的启动检查或资源版本管理超出此次小修补；暂不采用。若重新初始化 Arcfold 界面不能解决现场条件，先报告事实和所需范围，不继续扩大。

## 验收标准

- 审阅前重新完成真实旧版安装、消息、下载失败恢复、更新和一次确认；记录界面切换过程，确认没有强制整页刷新，并实际发送首条原生消息。
- 保留 A79 的只读配置对比，不读取真实密钥。按相同声明补入本地插件、Anthropic/OpenAI/灵眸 Claude 三个连接和默认 High，核对保留、选择、归因/主回答/学习调用；全部使用本机合成服务。重跑全新资料首条消息、原生配置刷新、正常退出重开读回。
- 检查和独立审阅通过后合入，双构建，再用最终原包做普通账户完整验收；通过才发布 GitHub/npm，并给出日常 DSH 更新步骤。

## 风险

重新初始化界面需要等待异步注册完成，不能把“保存成功”当作“界面可用”。本机合成结果不证明三个真实供应商的密钥、可达性或回答质量。
