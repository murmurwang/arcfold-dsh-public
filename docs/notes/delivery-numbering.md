## 问题

当前交付用任务名、仓库级请求号和分散回执关联。开发者不能仅凭一个总号查齐决策、反馈、审阅、发布与实际验收；工作流反馈也没有实际入口源码版本记录。

## 方案

按下附完整规范实现。入口为新交付自动分配总号，F／D／A／R 各自编号。独立反馈与 dev 反馈可先登记，后续只添加或纠正关系。确认、答复和执行证据写回所属材料或交付历史。已确认 D 改变后新增 D 并重新确认；原交付总号保留。公开提案、独立报告和更新说明显示交付号，私人内容留在本机。

实现沿用当前登记、开分支、测试、审阅、合入、发行、验收链路；新增本机编号与关系记录、查询及兼容迁移入口，不新增模型调用。先提供只读迁移对照；核对后才建立映射，旧文件与授权对象保持原样。本次开发交付工具，不发布插件包，不改日常安装与配置。

```text
登记交付／材料 → 入口分配唯一编号并保存来源 → 执行或追加确认与证据
                                      ↓
                         按总号或材料号读取事实和关联
                                      ↓
                         显示全部历史、下一步与待处理项
```

## 预期效果

一个总号可追溯整次交付；反馈可以先记后分；失败与未知结果始终可见；原话、独立判断、执行事实和记录责任分开保存。

## 考虑过的其他做法

仅改标题无法保证真实关联；将全部反馈强制归入交付会阻碍先登记；将开发、发布、验收再编字母号增加理解负担；重命名旧记录会破坏历史引用。按指定规范保留四类材料、稳定引用和兼容映射。

## 验收标准

- 总号查询能读取范围、全部关联材料、执行历史、待处理事项、上线与验收的分别状态。
- 交付号及 F／D／A／R 自动分配，完整编号唯一、不回收，并发或失败不能复用编号。
- F 支持交付内、独立和 dev 三种序列；独立 F 接续旧记录，关联与重新分类不改编号、不复制原话。
- dev 反馈保存真实入口源码、规则或明确未知原因，后续任务不以日常包版本替代 dev 版本。
- 决策草稿原号修改，已确认正文变化新增 D，重新确认前不能启动或提交受影响的开发；旧内容与确认可查。
- 请求改动新增 A 并保留旧请求、答复和绑定；步骤写回原 A，模糊答复不授予权限。
- 相同审阅预览或结果核对不增加 R，新请求增加 R；旧请求结果或费用未知时不能换号绕过。
- 每项材料保存来源、时间、作者、记录者，独立报告保留实际审阅者，授权和观察不由程序捏造。
- 未解决反馈即使已关联仍出现在总览；失败、拒绝、取消及未知结果保留，发布成功不等于验收通过。
- 迁移先生成归属对照且核对内容；旧文件不改名、不重写，旧授权不因映射扩大。
- 离线检查覆盖完整交付链路、历史兼容、编号竞争、失败恢复、越界授权和公开内容边界，使用合成资料。

## 风险

多文件写入可能中断，编号预留与恢复必须保留空缺和失败证据；旧任务和旧请求缺少完整归属，迁移必须显式核对。源码检查通过不代表开发者已接受实际入口体验；付费独立审阅和合入另按现有流程推进。

### 规范全文：交付编号、内容归属与记录责任



### 1. 总规则

一次准备执行的交付分配一个总号，例如 **001**。从准备决策、开发、审阅到上线和实际验收，都使用这个总号。

交付内材料通常写成 **总号-类型字母序号**，例如 **001-R2**，表示交付 001 的第二份独立审阅报告。D、A、R 必须带交付总号；F 还允许 **F1** 和 **dev-F1** 两种不带交付总号的写法，见第 3.1 节。

```
交付 001
├─ F：本次交付反馈   001-F1、001-F2；也可引用 F8、dev-F3
├─ D：决策文档       001-D1、001-D2
├─ A：请求单         001-A1、001-A2
├─ R：独立审阅报告   001-R1、001-R2
└─ 执行历史与进度
   ├─ 对齐、开发、测试、合入
   ├─ 构建、发布前验证、正式发布
   └─ 实际更新、验收、返工或结束
```

本文的“入口程序”，指 `Arcfold-DSH-Development` 命令背后负责分配编号、保存记录、核对结果和显示进度的程序。“交付主记录”，指打开 001 时看到的范围、材料目录、执行历史、下一步和等谁。

编号由入口分配。Agent 负责组织材料和执行工作；开发者 决定产品范围、确认方案、给出授权和真实体验；独立审阅模型负责独立审阅结论。记录者和内容作者分别保存。

示例中的编号、版本和结果均是假设，不代表已登记或执行。

### 2. 每一类由谁写、怎样编号

| 类别 | 谁提供或撰写内容 | 谁确认或作出判断 | 编号规则 | 何时增加新编号 |
|---|---|---|---|---|
| 交付主记录 | Agent 登记标题、问题、范围和来源；入口汇总实际材料与进度 | 开发者 决定交付范围及需要产品判断的变化；入口根据实际证据显示状态 | 001、002、003……；一次完整交付一个总号 | 开始准备一件新的独立交付时分配。登记草案本身不代表获准开发。 |
| F 反馈记录 | 开发者 或实际提供者给出观察、意见和截图；Agent 通过入口原样登记，注明来源与反馈对象 | 提供者对自己的描述负责；Agent 的分析单独标明，不能冒充原话 | 三种写法：001-F1（具体交付）、F1（独立反馈）、dev-F1（dev 工作流反馈） | 新反馈按第 3.1 节选择形式；实质更正在原序列增加一条并引用旧反馈。关联到交付或改正分类时不换号。 |
| D 决策文档 | Agent 根据真实场景起草、解释方案并按 开发者 意见修改 | 开发者 阅读具体内容并明确确认；Agent 登记确认原话与对应内容 | 001-D1、001-D2…… | 首份为 D1；未确认草稿可原号修改。已确认正文改变时增加 D2，并重新确认。 |
| A 请求单 | Agent 写清需要决定、批准或操作的事；开发者 提供答复；入口登记双方内容 | 开发者 选择、批准、拒绝或回报操作结果 | 001-A1、001-A2……；决定、授权、操作三种请求共用 A 的计数 | 每张独立请求增加一个 A。发出后改变请求内容或授权对象，另开新 A，关联旧单。 |
| R 独立审阅报告 | 入口组织固定材料；独立审阅模型给出报告；入口校验并归档，Agent 负责索引与后续处理 | 独立审阅模型作出审阅判断；入口核对证据和阻塞项。实现者不能代写独立结论 | 001-R1、001-R2…… | 准备一次新审阅时预留 R；再次实际发起独立审阅使用新 R。重复预览、读取或补核对同次结果不换号。 |

只有 F、D、A、R 四类独立材料使用字母编号。没有某类材料时，不为凑齐类型建立空文档。

原始反馈与独立报告保留作者身份。Agent 可以整理导航、解释结果和补充自己的分析，但不能把自己的推断写成 开发者 的观察或独立审阅者的原结论。

### 3. 具体编号规则

| 规则 | 写法与含义 |
|---|---|
| 总号范围 | 当前仓库内连续分配，至少三位：001、002……999、1000。已有编号不因位数增长而改写。 |
| 编号格式 | 交付内使用半角连字符、大写类型字母和从 1 开始的整数，如 001-D1、001-A12。F 例外允许 F12 和 dev-F12；dev 固定小写，F 固定大写。 |
| 同类计数 | 交付内分别统计 F、D、A、R。另有仓库级 F 和 dev-F 两条反馈序列，各自递增。001-F1、F1、dev-F1 是三个不同的完整编号。 |
| 完整引用 | D、A、R 引用必须带总号，如“批准 001-A2”。F1、dev-F1 本身就是合法完整反馈号，不是省略了交付总号的简称。 |
| 自动分配 | Agent 不自行猜下一个号码；入口统一分配并防止并发重复。 |
| 不重复使用 | 已分配的号码即使失败、放弃或取消也不回收；保留状态和原因，允许出现空缺。 |
| 不用号码推断进度 | 字母表示内容类型，末尾数字表示同类次数；实际先后按时间记录。001-R2 不代表“第二个阶段”。 |
| 分步请求 | 同一操作单的步骤写“001-A3 的第 2 步”，步骤答复存在原单中，不再分配新的材料号。 |
| 共享来源 | 已编号材料可以被其他交付引用，仍用原完整编号，注明来源关系；引用不会扩大旧授权的适用范围。 |
| 尚未归类的反馈 | 立即用 F 序列登记原话、时间和附件，不必先创建交付。后来确定归属，只增加关联，原 F 号不改。 |
| 归属登记有误 | 保留原编号、原归属和纠正记录，建立可查的正确关联，不静默改号或抹去来源。 |
| 外部原生标识 | 代码提案号、GitHub 问题单号、源码提交标识和安装版本保留原样，关联到总号；不再给它们重复分配 C、I、P 等别名。 |

### 3.1 F 的特殊规则：先有反馈，也可以先没有交付

“不绑定数字”指不要求先绑定 001 这样的交付总号。反馈仍需要自己的流水号，才能引用、处理和回查。

dev 在这里指本项目的开发入口、编号与请求规则、独立审阅及发布工作流；它不是“当前处于开发阶段”的简称。dev 仍是 F 的反馈对象标记，不增加第五种材料类型。

| 反馈场景 | 编号方式 | 谁登记、谁分号 | 例子 |
|---|---|---|---|
| 明确针对某次交付的改动或验收结果 | 001-F1、001-F2……；该交付的 F 序列 | Agent 按原话登记并明确交付；入口分配 | “001 改完后，重启仍然丢名称。”登记为 001-F1。 |
| 没有交付号、暂时不知道归属，或希望先记下再判断 | F1、F2……；仓库内独立反馈序列 | Agent 直接登记，不要求先开任务；入口分配 | “界面有时会卡住，还不知道和哪次改动有关。”登记为 F8。 |
| 针对 dev 工具或协作流程本身的一般反馈 | dev-F1、dev-F2……；仓库内 dev 反馈序列 | Agent 标明反馈对象是 dev；入口分配 | “next 没列出未归类反馈”“审阅费用说明难懂”“编号太复杂”。登记为 dev-F3。 |

三条计数规则：

1. 每个交付的 F 单独计数，独立 F 和 dev-F 各有自己的仓库级序列。入口保证完整编号唯一、不回收。
2. 独立 F 接续现有全局 F 序列，保留已有 F1 等记录；不能从 1 重开并覆盖旧反馈。没有既有记录的序列从 1 开始。
3. 第一次登记按对象选择形式。若明确是在验收某次 dev 改造交付，例如“007 约定修复的进度显示仍不对”，使用 007-F1，并把反馈对象写为 dev；对 dev 通用规则或工具提出意见则用 dev-F1，可以另关联其发生时的交付。对象不清楚时先用独立 F，不猜归属。

**编号分配后保持稳定，分类、去向和交付关联另外保存。**

| 后来发生什么 | 怎么登记 |
|---|---|
| F8 后来确定要由交付 007 处理 | 007 的来源写 F8，F8 增加“交付 007 处理”的关联；不改名成 007-F1，不抄一份新的反馈。 |
| dev-F3 需要修改开发入口 | 为这次改动登记普通数字交付 008；008-D1 引用 dev-F3。决策、请求和审阅仍用 008-D1、008-A1、008-R1。 |
| dev-F3 发生在交付 001 的执行过程中 | 可以关联 001 作为发生场景，另关联 008 作为处理它的交付。两种关系写清，不默认 001 已负责解决它。 |
| F8 后来被判断为 dev 的问题 | 保留 F8，把反馈对象更新为 dev，并保存分类依据和时间；dev 反馈视图按对象包含它，不改成 dev-F号。 |
| 一条反馈影响多个交付 | 保留一份原话和原号，分别建立关联并写明是发生场景、处理来源还是验收依据。 |
| 暂时只记录、不安排交付 | 可以长期保持不绑定总号，写明只记录的原因；仍可按原号查询。 |
| 反馈已关联交付，但问题尚未解决 | 只更新关联，仍列为待处理；挂上交付号不能自动变成“已处理”。 |

登记 dev 反馈时，除原话、提供者、时间和附件，还要记录：

- 针对哪个命令、界面、文档或协作规则，以及发生场景和实际输出（有则保存）。
- 当时实际使用的 dev 入口源码提交、所改文件或规则版本。无法取得时写“未知”及原因，不从日常安装版本推断。
- 相关交付、请求单或报告（可以没有），以及反馈的处理去向。
- 作为背景读到的日常 DSH 安装版本可以保留，但不能用它代替 dev 的发生版本。

一般建议或偏好没有可复现的执行现场时，照样可以登记，标明是建议或意见，不伪造版本、日志或体验结果。

dev-F 不触发一套 dev-D、dev-A、dev-R 编号。需要开发时仍建立普通数字交付，按已确认决策执行；是否需要发行安装包由该交付决定。反馈登记本身只保存输入与去向，不替代方案确认或实际操作授权。

### 4. 不单独编号的动作：谁做、谁记、记在哪里

| 动作或状态 | 谁执行或提供结果 | 谁记录、写到哪里 | 必须保留的依据 |
|---|---|---|---|
| 决策对齐、确认 | 开发者 明确确认具体方案 | Agent 经入口登记到 D 的附属确认记录；若有对应 A，同时写回答复 | 原话、时间、所确认的具体内容。决策正文不因状态变化被改写。 |
| 批准、拒绝、选择 | 开发者 答复 | Agent 经入口写回对应 A 的答复与状态 | 原话、选项、时间、授权的实际对象。模糊答复不自动算同意。 |
| 操作单分步完成 | 开发者 或单上明确获准的执行者操作并回报 | 写入对应 A 的步骤结果；体验观察另登记 F 并互相引用 | 执行者、步骤、时间、结果与证据。 |
| 开发、开分支、改代码、提交、同步公共代码 | Agent 在独立开发目录执行 | 工具与入口保存到交付的开发执行历史，Agent 补充必要说明 | 对应 D、目录、代码提案、实际提交和失败记录。 |
| 自动检查、测试、修复、重试 | Agent 发起，工具产生实际结果 | 工具保留日志，入口关联到对应代码、审阅材料或发布记录 | 检查对象、运行时间、结果和证据；新代码不能沿用旧代码的通过结果。 |
| 发起审阅、等待、收到报告、执行失败 | 入口在有效费用授权下调用独立模型 | 保存到对应 R 的执行记录；返回的报告归入该 R | 送审决策、实际代码、检查结果、请求和服务回执、费用核对。 |
| 合入 | Agent 通过已登记入口发起 | 入口把平台读回结果写入交付的合入记录 | 实际代码、通过的 R、检查、合入提交、时间和结果。 |
| 构建、发布前验证 | Agent 构建；实际测试操作者执行验证，需要 开发者 操作的部分用 A 请求 | 入口保存发行回执，测试操作者提供证据，汇入交付发布历史 | 源码、具体安装包、版本、环境、检查项目和实际结果。 |
| 正式发布 | Agent 在授权范围内执行；需要账户本人确认时由 开发者 操作 | 入口和 Agent 核对实际发布结果，保存到交付发布历史 | 对应 A、实际安装包、版本、上架与下载结果。 |
| 日常更新 | 开发者 操作，或 Agent 在绑定实际对象的授权下操作 | 操作结果回到 A，实际体验反馈记 F，交付记录显示进度 | 实际安装版本、执行结果、观察与截图。 |
| 验收、闭环 | 开发者 提供真实体验；Agent 对照已确认标准登记结果 | 验收记录放在交付主记录下面，引用 D、F 和实际版本，由入口汇总 | 通过／失败／未确认、判断依据、观察者、记录者和时间。不能以发布成功代替用户验收。 |
| 暂停、恢复、放弃、被替代 | 按 开发者 的指示或已确认处理规则执行；涉及范围取舍由 开发者 决定 | 入口保存交付状态变更，Agent 写明原因与来源 | 原因、时间、相关答复和替代关系。 |
| 后续问题的处理 | 独立审阅模型或 Agent 提供发现；Agent 调查并提出去向，涉及产品判断由 开发者 决定 | 保留在 R 的发现、已有 GitHub 问题单或交付的待处理事项中 | 出处、具体问题、证据、负责人及处理去向。 |
| 进度查询和展示 | 入口读取实际记录，Agent 向 开发者 说明 | 主记录、查询结果和进度页面由事实生成 | 当前阶段、下一步、等谁、待答 A、未解决事项、结果未知的写入。 |

去掉 C、P、V、I 只减少面向人的编号。实际的代码、发布、验收、问题和操作证据仍各自保存，可以从总号查到。

“已开始”“已完成”“已失败”是动作状态；“通过”“未通过”是有依据的判断。不得用前者自动推导后者。

### 5. 四类材料必须包含什么

| 类别 | 最少内容 | 可以追加的状态 |
|---|---|---|
| F | 完整编号、提供者、原话、时间、反馈对象、相关交付（可为空或多个）、来源、附件、处理去向；按对象记录产品安装版本或 dev 的入口源码版本，未知时明说 | 待归类、待处理、已关联决策、已作为验收依据、只记录及原因。Agent 分析与原话分开；有交付关联不等于已经解决。 |
| D | 完整编号、来源 F 或问题单、真实问题、范围、方案、预期效果、备选、验收标准、风险、前一份 D（如有） | 草稿、待确认、已确认、被取代、取消；确认原话和时间保存在附属记录中。 |
| A | 完整编号、请求类型、场景、实际后果、需要回复什么、绑定对象或关联材料、可照抄的答复；有步骤则逐条列明 | 待答、已答、分步结果、被替代或取消；历史答复和原始请求保留。 |
| R | 完整编号、独立审阅者、对应 D、实际代码及基线、固定送审材料、检查证据、费用授权、执行结果、原始报告和可定位证据 | 待送审、等待答复、已返回、执行失败或结果未知；报告尚未返回时不能写成“审阅已通过”。 |

R 的编号可在准备材料时预留，以便费用请求引用它。只有实际收到并核对报告后，才有独立审阅结论。查询同一结果不会新增 R；新的独立请求增加 R。旧请求的结果或费用未知时，先核对，不用新号绕开旧的不确定记录。

A 的决定、授权、操作三种用途共用同一套编号，不再分别加类型字母。已有明确答复按原话登记到对应对象，不要求 开发者 为同一件事重复批准。存在多张未答单且回复无法对应时，需要明确编号，不能由 Agent 猜选哪张。

### 6. 修改、返工与重新编号

| 情况 | 编号怎样处理 | 谁负责后续 |
|---|---|---|
| 决策尚未确认，讨论中修改草稿 | 仍是 001-D1 | Agent 修改并展示全文或改动，开发者 判断是否对齐。 |
| 已确认决策正文需要修改 | 新建 001-D2，引用并保留 D1；交付总号仍为 001 | Agent 停下受影响的执行、展示新决策；开发者 重新确认后再启动相应执行。 |
| 反馈需要实质更正 | 在原形式对应的序列中新增一条并引用原反馈，例如 F8 更正为新记录 F9、dev-F3 更正为新记录 dev-F4；不覆盖原话。只改分类或关联不新增反馈 | 原提供者给出更正，Agent 登记。仅补附件也要记录补充时间和来源。 |
| A 已发出，内容、对象或费用边界变化 | 新建下一张 A，注明取代关系；旧单的答复不迁移成新授权 | Agent 写清变化，开发者 答复实际的新请求。 |
| 代码修复、重开开发目录或代码提案，方案未变 | 总号与 D 不变，更新执行历史和实际代码关联 | Agent 执行、测试并提交；此前审阅只对原代码有效。 |
| 再次发起独立审阅 | 新建 001-R2，保留 R1 与实际结果 | 入口确认材料、授权与旧请求结果后发起，独立模型给出新报告。 |
| 发布版本或安装包变化 | 总号不变，保存新的发行回执和所需授权，不编 P | Agent 核对具体内容；需要 开发者 批准时使用新 A。 |
| 已上线但验收失败，仍需完成本次交付 | 总号仍为 001；新反馈增加 F，后续方案或审阅按上面规则增加 D／R | Agent 保存失败、调查修复；产品方案变化由 开发者 判断。 |
| 一次交付已经完成，另开展新交付；或另做独立的事 | 分配 002，并注明来自 001 的哪条材料或问题 | Agent 提出划分；涉及交付范围与优先级的判断由 开发者 决定。 |
| 交付取消或长期保留待处理 | 总号及已有材料都保留，写明当前结果和原因 | 按实际决定登记，不复用编号，也不把取消写成验收通过。 |

追加确认、答复、执行状态或证据不会自动生成新材料号。只有独立内容或一次独立审阅按规则需要新记录时才增加编号。

### 7. 从反馈到上线的一次完整示例

| 顺序 | 谁做什么 | 内容与编号 | 写入的结果 |
|---|---|---|---|
| 1 | 开发者 反馈改名后重启失效；Agent 登记准备处理的交付 | 总号 001，反馈 001-F1 | 原话、版本、截图和来源。 |
| 2 | Agent 写方案、范围和验收标准 | 001-D1 | 决策草稿。 |
| 3 | Agent 请 开发者 确认；开发者 明确答复 | 001-A1 关联 001-D1 | 请求答复和 D 的确认记录；不新编确认号。 |
| 4 | Agent 开发并运行检查 | 001 的开发执行历史 | 实际代码提案、提交及测试结果。 |
| 5 | 入口准备固定审阅材料；Agent 请求费用授权 | 预留 001-R1；请求 001-A2 | 费用请求明确指向该次材料，或明确的累计费用上限与对象。 |
| 6 | 开发者 授权后，入口调用独立模型 | 001-R1 | 原始报告、证据、实际回执及费用核对。 |
| 7 | 检查和独立审阅通过，Agent 经入口合入 | 001 的合入记录 | 对应代码、R1、实际合入提交。 |
| 8 | Agent 构建，测试操作者完成发布前验证 | 001 的发布历史 | 源码、具体包、版本和验证证据。 |
| 9 | Agent 请求正式发布；开发者 批准 | 001-A3 | 绑定实际安装包和版本的授权。 |
| 10 | 获准后发布并核对上架结果 | 001 的发布历史 | “已上线，版本 0.4.2”及实际回执。 |
| 11 | Agent 请 开发者 更新并回报 | 001-A4 | 操作步骤及需要回报的结果。 |
| 12 | 开发者 实际更新并给出体验 | 001-F2，关联 001-A4 | 观察原话、实际安装版本和截图。 |
| 13 | Agent 对照 D1 的验收标准登记结果 | 001 的验收历史 | 依据 F2 和实际版本写通过、失败或未确认。 |

若实际需要额外的操作单或决定单，A 序号顺延；这些示例号码不是预先固定的阶段编号。

上线与验收分别记录。安装包上架后可以说“001 已上线”；只有实际体验证据满足约定标准，才写“001 已通过验收”。证据不足时保持未确认。

### 8. 总号下面必须能查到什么

| 区域 | 内容 | 维护者 |
|---|---|---|
| 交付范围 | 标题、要解决的问题、来源、当前生效 D、与其他交付的关系 | Agent 登记；涉及产品判断由 开发者 决定。 |
| 材料目录 | 全部交付内材料，以及关联进来的独立 F 和 dev-F；包括被取代、拒绝、失败和取消的记录 | 入口按真实关联维护目录，不能只按总号前缀筛选。 |
| 执行历史 | 开发目录、代码、检查、审阅请求、合入、构建、发布、实际更新 | 工具与入口保存事实，Agent 补必要说明。 |
| 待处理事项 | 本交付的未答 A、审阅问题、相关反馈、验收缺口和结果未知的写入；仓库总览还要列出尚未关联交付的 F、dev 反馈与其去向 | 入口汇总，Agent 明确去向和下一步。未绑定数字不能成为遗漏反馈的理由。 |
| 发布与验收 | 各次实际版本、包、发行回执、反馈依据和验收结论 | 入口关联；Agent 按实际结果登记。 |
| 当前进度 | 到哪一步、下一步是什么、等谁、是否已上线、是否已验收 | 入口从记录推算，Agent 对外说明。 |

只读查询总号 `001` 时展示全过程及所有关联反馈，包括原号仍为 `F8` 或 `dev-F3` 的记录；查询 `001-D1` 或 `001-A2` 时展示具体材料。查询 `F8` 或 `dev-F3` 时展示原话、对象、处理状态、全部关联和历史。拟议的 `dev` 反馈视图按反馈对象筛选，包含后来被归类为 dev 的独立 F，而不只匹配 dev-F 前缀。

LOG.md 只记事件与证据链接，不手写维护权威进度。展示页即使有“状态”栏，也来自实际记录；不能靠改一段文字就把交付标成完成。

### 9. 文档、公开内容与原有标识

- 独立材料标题使用完整编号，例如 `[001-D1] 修复目标改名后重启失效`、`[001-A2] 独立审阅费用请求`。
- GitHub 代码提案和问题单显示所属交付，如 `[交付 001] …`，同时保留平台自己的号码。
- 公开审阅报告使用完整 R 号。发行版本保持实际版本号，更新说明注明交付总号及代码提案。
- 公开文本不包含反馈原话、私人截图、请求单正文或凭据；这些保存在本机。公开需要的决策内容按已有审阅与隐私要求处理。
- 截图、测试日志、模型回执和安装包归在相应材料或执行记录下面，不新增字母种类。
- 每项实际记录都保留来源、时间、内容作者、记录者及证据位置；D／A／R 保留所属交付，F 保留反馈对象和关联交付列表，允许尚无交付。涉及实际操作时保留授权依据。
- 文件可以继续按现有工具需要存放，统一引用由入口维护。不能只改标题而缺少真实关联，也不要求把所有机器记录塞进一份文档。
- 新编号生效前，已有 A4、旧任务名等仍按当前入口使用。迁移先展示归属对照并核对，旧文件不改名、不重写，旧授权不因映射被扩大。

### 10. 当前源码依据与实施边界

本次以以下已有机制为实施基础。现有入口的以下机制可以沿用：

| 当前实现 | 已有行为 |
|---|---|
| `collab.py:create_ask / answer` | 创建请求，保存原话、步骤、答复状态和授权对象。 |
| `collab.py:record_feedback` | 现已生成仓库级 F 号，保存原话、日常包版本和附件；这能承接独立反馈，但尚无交付内 F、dev-F 和按反馈对象记录版本的能力。 |
| `collab.py:align` | 保存确认原话及所确认的决策内容，确认记录与正文分开。 |
| `workflow.py:start / submit` | 从已确认决策建立独立开发目录，保存代码提案与实际提交。 |
| `desktop_review_request.py:request / validate` 与 `workflow.py:review` | 组织固定材料，调用独立模型，校验有证据的报告并保存回执。 |
| `workflow.py:confirm_merge` | 保存实际合入的代码、基线和结果。 |
| `release.py:prepare / verify_isolated` | 保存源码、具体包、构建结果，并核对发布前验证对应同一批包。 |
| `workflow.py:close_loop` | 关联反馈、版本、源码、包、结论和时间。 |
| `collab.py:progress` | 读取本机记录，推算进度与待处理事项。 |

当前 `new_from_feedback` 会从反馈里的日常包版本预填发生版本。处理 dev 反馈时，需要改为使用入口的实际源码版本或明确的未知说明，不能把日常 DSH 包版本当作 dev 版本。现有 `entry_commit` 可读取入口提交，但目前反馈登记并没有自动保存它。

编号分配、关联和查询不需要新增模型调用。独立审阅仍走现有费用授权与回执核对流程。


### 11. 验收这套编号规则

- 只报总号，能查到整次交付从决策到上线和实际验收的全部记录。
- 每类材料都能分清内容作者、判断者、记录者；Agent 不替 开发者 或独立审阅者写结论。
- 编号由入口分配，无重复、无回收；D／A／R 带总号，F 支持规定的三种完整形式，跨交付引用保持原来源。
- 独立 F 可以在没有任何交付时登记；dev-F 可以在没有产品安装版本时登记，并保留 dev 的实际版本或未知说明。
- F、dev-F 关联到交付后不改号、不复制原话；按总号查询能找到它们，按反馈号查询能看到全部去向。
- 将独立 F 后来归类为 dev 时，编号不变，dev 反馈视图仍能找到它；未关联交付的反馈不会从待处理总览消失。
- 草稿修改、确认后修改、请求变更、重复查询和再次审阅分别按规则处理。
- 开发、发布、验收和后续问题虽没有额外字母号，仍有可定位的实际记录和证据。
- 失败、拒绝、取消和结果未知的历史保留；进度不会把未知写成通过。
- 已上线与已验收可以分别查询，旧授权始终对应原实际对象。
