## 问题

本次新后端进程25213启动于2026-11-25 00:51:13 PST，旧进程已退出。新启动计时总77.051秒，其中恢复已完成任务的后续检查76.361秒；其余已计时步骤总计0.690秒。上次总128.498秒，本次仍明显慢，不算速度验收通过。

源码调用链：src/tree/runtime.mjs的recover遍历所有已提交任务→afterCommit对每条学习调用ReflectionTriggers.scan→src/tree/metrics.mjs逐类调用ClusterService.candidate→src/tree/clusters.mjs重复调用EpisodeSignals.episodes→src/tree/signals.mjs重新整理历史信号、核对原文和计算分类。数据副本有85条已完成学习；最多的一个目标对应33条。同一份历史在每条学习恢复时重新扫描。

用测试版只读快照及真实会话日志运行当前源码：11类候选检查一轮约0.9—1.0秒，再跑一轮仍约0.9秒；热点不只在数据库读出，还包括重复计算、原文核对。总耗时归因与源码和实际76秒一致，但不把乘法估计当作逐函数完整计时。证据：requests/test-f57-runtime-reload/restart-observed.json及after-restart-profile.json。

085已有速度测试在420条合成任务上调用recover，但把afterCommit替换成空函数，跳过了本次76秒的真实调用链；所以原测试通过不能证明完整启动快。不是“重启没做好”。

加载等待需分开：实际副本中单次目标详情约9毫秒、轮次详情约110毫秒；这不代表真实界面端到端耗时。00:55观察到会话已加载，模型仍在生成，界面显示约11 tok/s。模型生成和连接等待不归入本次本地计算优化的效果承诺。

## 方案

1. 保留每条任务恢复、检验触发、来源核对和记录的语义。让同一份未变化的历史统计在恢复及一次后台扫描中复用，避免按每条历史任务、每个类别重复计算。按实际记录和原文版本核对可复用范围；写入、撤回、更正或原文变化后必须重新计算，不复用旧判断。不靠删历史、关闭学习或跳过检验提速。
2. 为反复按轮次查询历史事件的统计路径建立一次性查询映射，同一轮计算共用；保留来源边界和原有结果顺序。具体实现以可证明结果相同为准，不以减少触发次数替代。
3. 补完整恢复测试，执行真实afterCommit、分类统计、原文核对及检验触发；模拟的只有付费模型端，绝不为性能验收发送真实模型请求。测目标详情、轮次详情及本地等待；把数据读取、统计、模型等待分别记录，不能把服务器等待当成本地性能。
4. 从开工当时GitHub main独立开发，经相关检查、既有预算内自动审阅和CI后合入。安装到体验环境仍另按实际提交开授权单。

## 预期效果

减少启动和后台检查阻塞本机的时间。采用这份数据规模作为回归基准，目标是完整恢复步骤低于5秒、Arcfold已计时启动低于10秒；这是验收目标，尚未实现。网络失败和模型每秒输出速度仍单独调查，不承诺靠这项修改消失。

## 考虑过的其他做法

反复重启：已经排除，不能修复重复计算。只调整085任务表读取：热点已进入其后的真实统计链。删历史、少做检验：会改变功能或丢证据，不采用。无依据更换模型或代理：不属于本次授权。

## 验收标准

- 同一份数据前后对照：完整恢复走真实后续检查，恢复步骤低于5秒、Arcfold已计时启动低于10秒。记录机器负载与数据规模，不以空函数替代热点。
- 旧、新实现恢复生成的任务、触发归属、判断结果及顺序一致；已有任务不重复派发，未完成的后续工作不能遗漏。
- 新增记录、原文变化、撤回、更正、其他数据库连接写入后，统计及时失效；不同目标或不同数据版本不串用结果。
- 本地目标、轮次详情读取结果与旧实现相同；相关恢复、后台学习和检验测试通过。
- 真实界面验收另记，未观察之前保持unconfirmed；本地改动不改变模型、提示词、工具、计费、超时或连接配置。

## 风险

复用范围过大会使用过期判断，因此必须有变化后的失效和结果一致检查。实际界面加载还可能包含其他路径，需计时后再下结论。本次不新增付费模型请求；代码审阅沿用既有预算规则。
