# 决策：允许未发布版本修补候选并保留每次验证证据

## 来源

开发者反馈 F3：质疑补齐许可为何使未发布的 0.5.0 必须改成 0.5.1；查明当前工作流按版本唯一绑定源码与构建记录。开发者随后要求「起草一个方案」。本次仅登记决策草案，尚未对齐或启动开发。

## 问题

0.5.0 已合入并在本机构建，发布前发现第三方许可材料需要补齐。当前工作流却要求修补版本高于主分支版本，使尚未公开的候选也只能升为 0.5.1。

源码中有三处相连的限制：`workflow.py:release_notes` 要求版本递增；`confirm_merge` 将一个版本唯一绑定到一个合入提交；`release.py:release` 按版本读取已有构建记录。入口还会在隔离验收之前创建 GitHub 版本标签和发行草稿。它们保护了旧证据，却没有提供保留证据后的同版本返工路径。

## 方案

**1. 分开保存发行版本与每次候选。** 发行版本是用户最终安装时看到的号码，例如 0.6.0。每次登记准备交付的源码，连同其安装包和验证记录，称为一次候选；可以有“0.6.0 第一次候选”“0.6.0 第二次候选”。这些例子不代表实际版本选择。合入时即登记候选，可以处于待构建状态；之后追加构建与验证结果。每次候选保存源码提交、所含改动及审阅记录、构建输入、核心包与界面包的内容校验值、验证结果和被哪次候选取代。校验值用于识别文件内容是否完全相同。已保存的源码身份、原包和证据不覆盖；两份包始终作为一组选择和发布。候选身份供入口核对，不新增面向开发者的 C、P 等材料编号。

**2. 同版本修补必须有明确来源。** Agent 登记修补时，明确引用原候选和修补原因。入口核对版本仍等于当前主分支中的目标版本、原候选仍是本次修补的有效来源，并查询 GitHub 标签、发行及 npm 两份包的状态。只有未对外写入且无结果未知的操作，才允许同版本修补；新发行仍须递增，低于主分支的版本仍拒绝。检查在提交审阅材料时和合入前都执行，不能等远端合入成功后才发现登记冲突。源码改动继续经过正常检查、独立审阅和受管合入。

**3. 修补后生成新候选，重新验证。** 原候选记下不能继续发布的原因并保留原包。新源码合入后，入口追加该版本的合入记录，重新构建两次、核对两次产物一致，再保存新候选。旧审阅不证明新改动已通过，旧安装验收不证明新包已通过；新候选必须取得对应源码、对应整组安装包的适用检查及隔离验收结果。原改动与后续修补的证据均可回查。相同输入的命令重试继续同一次候选，实际输入变化才另存候选。主分支前进时仍沿用现有暂停核对规则，本期不增加任意历史源码发布能力。

**4. 把对外写入放到隔离验收之后。** `release --prepare` 只准备本机候选。隔离账户从该候选的本地包测试安装、对话、更新失败恢复、更新成功和重启读回；测试目录按候选隔离，避免同版本缓存混用。将决策和审阅中明确要求发布前完成的事项登记到候选待办清单，例如本次许可补齐，并逐项关联处理证据；普通后续建议不自动变成发行阻塞。待办、验收结果和所需授权均齐备后，才允许创建正式版本标签、上传附件并推进公开发布。普通 `release` 不再提前创建标签或草稿；缺少验证时只返回待办。最终操作显式绑定某次候选及两份包，禁止悄悄使用“最新候选”。npm 仍沿用现有授权发布路径，只将对象与结果纳入候选核对，本期不另建一套完整的自动发布服务。

**5. 开始对外写入后锁定内容。** 已有标签、发行草稿、公开发行，或任一 npm 包已经发布时，均不允许同版本换内容；这是本方案选择的保守边界。即使后来删除远端内容，已知发布过的版本也不恢复为可修补。写入结果未知时先查清；如果确认完全没有写入，保存核对依据后可以恢复修补。若两份包只成功发布一份，只允许继续完成原候选的另一份；需要修改包内容则另升版本。本地同一版本的写入串行执行，并在远端操作前重查状态；外部操作造成冲突时停止并核对，不覆盖远端。

**6. 旧记录与进度一起适配。** 为现有合入、构建、审阅和验收记录建立候选索引，保留旧文件原内容；已对外写入的旧版本直接锁定。资料不足时显示“待核对”，不能推断为未发布。`next` 同时显示版本、当前候选、阻塞原因和下一步；旧候选被取代后不再提示继续发布。发布授权至少绑定候选和整组包的内容，不能仅凭版本号把旧授权迁到新包；审阅费用仍按现有材料或累计费用范围核对。

**7. 与当前工作衔接。** A8 已确认补齐许可后采用 0.5.1，该交付继续按原决定推进。本草案不把它改回 0.5.0。等交付编号改造合入后，本任务从当时主分支开独立目录，沿用其交付、决策、请求单和审阅编号；候选历史归入交付的发布历史。实现范围是 `tools/dev-workflow/` 中的版本检查、合入登记、构建发布、隔离演练、进度及相关测试，并更新工作流说明。本次只改 dev，不因此增加 Arcfold 安装包版本。

## 预期效果

发布前发现问题，可以在原目标版本下修补并重新验证；每次失败、修补和通过都有独立证据。用户最终安装的版本对应一组确定的源码与安装包，开发者不用为了完成同一次发布前返工而反复决定新版本号。

## 考虑过的其他做法

继续每次修补都升号，最省实现工作，但保留了本次暴露的返工成本。只把版本比较改成“允许相等”，不能解决旧合入记录、构建记录和验收混用的问题。使用预发布版本号可以另行讨论，但会改变包版本及安装更新路径，本期采用内部候选历史即可覆盖这个场景。

## 验收标准

- 未对外写入的版本能完成第一次候选失败、同版本修补、第二次候选通过的全过程，旧记录原样保留。
- 未引用原候选、引用过期候选、降低版本或两份包版本不一致时，提交或合入前拒绝。
- 新候选不能借用旧候选的审阅、包验收或发布授权；缺少许可待办的处理证据、适用检查或隔离结果时不能创建远端标签与发行。
- 已存在标签或草稿、任一包已发布、曾发布后删除、查询失败、写入结果未知等场景均按上述边界处理；部分发布只能续传原包。
- 重复命令不重复登记；两个执行者同时修补或发布不会相互覆盖；测试中能识别同版本缓存导致的旧包误用。
- 旧 0.4.x、0.5.0 记录可回查，候选切换后 `next` 指向正确下一步，并与交付编号规则兼容。
- 用本地模拟远端验证拒绝、重试和部分成功，再按现有流程独立审阅；这些测试不发布真实包。正式使用时仍需实际候选的隔离验收及对应授权。

## 风险

主要风险是同版本缓存、旧记录转换和两个入口同时写入。用候选独立测试目录及内容核对、只追加索引、同版本串行写入应对；切换新版入口时暂停旧入口写入。已有 GitHub 标签或草稿的候选本期不支持原版本改包，这是有意保留的限制。方案确认只授权进入上述 dev 开发范围，付费审阅、公开合入发布及用户环境操作仍按各自已确认的授权推进。
