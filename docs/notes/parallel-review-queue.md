## 来源

开发者要求修改 A15 并开决定单：“A31 先不做。PR #26 的审阅排在 #18、#27、#23、#24 后面，轮到时 rebase 到最新 main，再重新开授权单。另外把‘付费审阅只给合入队列最前面的 PR’写进你的决策，开决定单给我看。”

原 A15、原确认、A27、A31 原话及已有代码、检查和费用证据保留。本修订另行登记，尚未对齐或启动；不覆盖已冻结的原决策，不将 PR #26 的第一批实现写成已启用。

## 问题

两项提案都在同一份主线上完成付费审阅时，前一项合入会改变后一项的基线。后一项仍要重新组合代码、检查并取得适用的独立审阅，旧报告可能只能留作历史。即使用两把独立密钥同时发送，也不能消除这次返工。

PR #26 当前实现的 `Workflow.merge` 在审阅通过后才调用 `merge_queue.enqueue`，尚不能决定谁可以开始付费审阅。A13 的 `review_queue.enqueue/process` 管理批准、发送和核账，需要接入提前确定的合入顺序。本次把等待点前移至付费发送之前，继续允许源码、检查和材料准备并行。

## 方案

### 对 A15 的明确修订

1. 第 2 节的独立模型审阅改为：**同一仓库只允许合入队列最前面的 PR 发起付费审阅**；其余 PR 可并行编码、检查、提交草稿和准备不收费的材料。不同专用密钥不能绕过队首限制。不同仓库分别判断自己的队首，同一计费密钥仍从发送到核账完成保持独占。
2. 第 4 节的队列改为：先确定合入顺序，再为队首准备最终组合、费用授权和独立审阅，不能等审阅通过后才登记。队首等待检查、授权或修复时，不自动跳过它给后面的 PR 付费审阅。
3. 第 7、8 节的衔接改为：A13 仍是唯一的受管发送和核账实现；人工入口和后台发送入口共用队首核对及原请求记录，不另建审阅程序或密钥记录。其余已确认的候选、编号、并行构建和检查拆分安排保留。

### 本轮顺序及 PR #26

固定顺序：**#18 → #27 → #23 → #24 → #26**。新提案默认追加队尾；调整顺序、后移或撤回队首须保存明确的决定及理由，不因后面的检查更早通过而自行插队。

A31 暂缓，旧启动入口停止发起请求。A27 仅保留为原材料的历史批准，不用于后续新材料。核对时 PR #26 尚未发起本次付费请求。

轮到 PR #26 后，先与当时最新 main 重新组合（rebase），解决冲突并完成对应检查，再生成审阅材料、核对费用依据和密钥额度，开新的费用授权单。旧材料、旧检查和旧授权不能冒充新组合的放行。已经在发送中的其他请求先核对原结果和费用，不因改顺序而取消、掩盖费用或重发。

### 从准备到合入

1. 每项任务在自己的目录开发，同时进行本地检查、GitHub 检查和不收费的材料准备。
2. 需要合入的提案提前登记到现有合入队列。`next` 显示队首、等待位置，以及各任务现在仍可做的步骤。
3. 队首读取最新 main、组合改动；通过对应自动检查后，准备最终材料和费用授权。
4. 发送前重新核对队首、固定提交、主线基线、检查、授权和 A13 的密钥占用。任一条件变化就不发送，并记录具体等待原因。人工和后台路径使用同一判定。
5. 从发送开始到审阅结果及合入核清，保留该提案的合入次序，后续受管提案不得抢先改 main。保留次序不等于长期占用主线写入锁：等待批准、模型或检查时不持有该锁，只在实际主线写入及核对时持有。
6. 队首审阅通过、合入并确认 GitHub 实际结果后，才提升下一项。审阅阻塞时由当前项修复；请求或写入结果未知时核对原对象，不重复发送。

如果 GitHub 被其他入口改动，发送前发现变化则停止；发送后才发现变化，保留旧报告和实际费用，不能自动转成新组合的放行。本方案减少受管队列内的重复费用，不承诺消除所有外部变更造成的返工。

### 剩余工作与启用

已提交的第一批代码保持可回查；临时目录中的候选、编号和审阅程序组合保留为预验证材料，不能当作正式主线或已经启用。修订确认后才启动对应实现，从启动时最新 main 开始，不直接修改其他任务的独立目录。

付费审阅轮次不阻止无关开发、候选构建或材料准备。最终组合消费前置合入结果时才等待。上线仍先部署兼容读取入口，再切换 GitHub 检查布局；候选组合通过后才启用保留候选的发行。继续沿用此前完成剩余工作和正式启用的授权；本决定单不追加模型费用，不授权修改日常 DSH、用户数据或凭据。

## 预期效果

后一项提案在前一项合入后，才为实际要合入的代码组合付费，减少明知基线马上改变仍提前审阅的重复开销。实现和检查仍可并行，进度能区分“等待审阅轮次”和“现在可继续的工作”。

## 考虑过的其他做法

- 多把密钥同时审阅同一仓库：请求能并行，前一项合入仍可能使后一项需要重新付费审阅。
- 只写文字规则：人工或后台入口可能漏看顺序，因此两处实际发送前都须查询同一队列。
- 等模型期间一直占用主线写锁：把长时间等待塞进共享操作；改为保留队列顺序，只在真实写入及核对时持锁。

## 验收标准

- 队首为 PR A 时，PR B 即使检查通过、持有费用授权并使用另一密钥，人工和后台入口也都不发送付费请求。
- 非队首仍可编码、提交草稿、准备材料和运行独立检查，`next` 同时显示这些可做步骤和等待位置。
- 两个执行者同时竞争发送时，只有真实队首可领取一次；重启、迟到结果、撤回授权及结果未知不会导致重复发送。
- 队首等待批准或模型时，主线写锁不被长期占用；后续受管合入仍遵守队列次序，不能抢先合入使已付费材料过期。
- 队首合入并核实结果后，下一项重新读取 main；新组合必须具有对应检查、材料和费用授权。
- 本轮顺序可读回为 #18、#27、#23、#24、#26；PR #26 轮到且完成最新组合、检查和新费用批准后才发送。
- 旧决策、报告、费用和失败证据保留；共用 A13 的发送与核账记录，不新增密钥保存方式。
- 本地模拟明确标为本地证据，不能宣称已完成真实付费审阅、正式合入或启用。

## 风险

队首难修或等待批准时，后续付费审阅会等待，这是本次明确选择的费用与并发取舍；其他开发和准备继续。确需调整顺序时留下决定记录，不自动插队。外部直接改变 main 仍可能导致重验或额外费用，不能用旧报告放宽新组合的检查门槛。
