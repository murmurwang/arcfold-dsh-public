# 决策：[040-D1] 每次启动自动记录 Arcfold 各步用时

Status: proposed
observed_in_version: 0.6.0
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F33（2026-11-19T12:04:50+00:00 登记）

## 问题

开发者在日常 DSH 0.6.0 打开应用后，程序坞里有图标但没有窗口，约 4 分钟后窗口才出来。系统日志里 11-19 的三次启动分别约 3 分钟、3.5 分钟、7 分钟才就绪。

现在没法知道这几分钟花在哪一步。产品启动时不记各步用时，原计划下次重启时手动带 CPU 记录启动，但至今没有录到：要靠开发者记得用特殊方式启动，慢的那次往往没录。

只读核对过日常的目标树资料（24 MB，5 个对话，154 个后台任务），数据量不大，不能据此认定是资料多导致的慢。

## 方案

在 Arcfold 插件启动时给每一步记开始和结束时间，按启动顺序至少包括：插件开始执行时 DSH 进程已运行多久、打开目标树资料库、模型记录恢复、读回历史对话、启动恢复里的各段处理（取消未提交的主任务、整理未结束的对话轮、处理失败的学习、重放已提交的任务）、后台开始运行。

每次启动结束（成功或在某一步报错）时，往 Arcfold 私有目录里的一个启动记录文件追加一行，写明版本、开始时间、各步用时和结果；报错时写明停在哪一步。文件只保留最近 50 次。同时在 DSH 日志里打一行总用时。

记录只有时间和步骤名，不写对话内容、目标内容、路径以外的资料或凭据。记录失败不影响启动。

## 预期效果

下次启动再慢，直接打开记录文件就能看到是哪一步占了时间，用不着开发者再配合重启。插件开始执行时 DSH 已运行多久这一项，能分清慢的是 DSH 本体还是 Arcfold。像 032-A8 这样启动报错，也能看到停在哪一步。

这项改动本身不让启动变快，修慢的问题要等拿到记录后另开任务。

## 考虑过的其他做法

每次启动都带 CPU 记录：录制本身会拖慢启动，文件也大，不适合一直开着。

每次都录 CPU、启动快就丢掉：能拿到更细的信息，但录制对启动的拖慢有多大没有实测，先不做。拿到分步用时后，如果某一步内部还看不清，再针对那一步另定。

只在超过某个时长时才记：要多一个阈值判断，好处不大，每次都记一行足够小。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

- 正常启动后，记录文件多出一行，包含版本、开始时间、上面列出的各步用时和结果「成功」。
- 让某一步抛错时，记录文件写明停在哪一步、错误代码，启动仍按原样报错，不被吞掉。
- 记录文件写不进去（目录不可写）时，启动照常完成。
- 连续启动超过 50 次后，文件只剩最近 50 行。
- 记录里不出现对话原文、目标内容和凭据。

## 风险

如果慢的是 DSH 本体、还没轮到 Arcfold，记录只能看出「插件开始时已过去几分钟」，具体慢在 DSH 哪里看不到。

每步计时要改动启动代码的多个位置，改错可能影响启动顺序。改动只加计时，不改原有步骤的顺序和逻辑，由现有启动和恢复测试兜底。
