# 决策：[021-D2] 从产品仓库移除本地维护的开发工具

fixed_in: pending

## 来源

开发者已安排开发工具转入独立本地仓库维护，并在产品修复提案合入后清理公开目录及相应工具检查步骤。产品修复已合入。后续明确将旧开发工具提案中描述产品或安装包行为的说明收进本提案，工具专用说明仍保留本地；本决策据此修订范围和交付顺序。

## 问题

产品仓库仍保留 tools/dev-workflow 下的工具源码，并在 Desktop 检查作业中运行它们的单元检查。工具已经转入本地仓库开发，继续保留旧副本会产生两个维护位置。移除目录后，原 CI 的工具检查步骤和公开 AGENTS.md 指向该目录的链接也需要同步处理。

起草时的入口强制要求 CI 回执含“运行工作流检查”，直接删除步骤会阻塞清理提案的审阅与合入。因此先完成本地兼容读取，并按既定条件启用固定入口；目前这项前置工作已经完成。

## 方案

1. 从开工时实际 GitHub main 建立本任务的独立目录，删除 tools/dev-workflow 的 20 个受版本管理文件；合入前重新核对目录清单。
2. 仅删除 .github/workflows/desktop-checks.yml 的“运行工作流检查”步骤，保留 Desktop 作业名称、macos-15、精确提交核对、依赖安装及产品模拟检查。
3. 调整公开 AGENTS.md 中指向被删目录的入口说明，明确开发工具独立维护；将原候选修补提案中描述两份安装包、候选验收、失败证据保留及公开后内容锁定的说明整理进 docs/release-bundle.md，移除指向已删除工具目录的链接。工具专用的编号、调度、命令及旧决策说明只保留本地补丁，不加入公开仓库。测试脚本的执行行为改动不是说明，仅保留本地，不并入本提案。新增本任务决策说明，不加入本机路径、私人记录或对话。
4. 本地工具的 CI 读取兼容在本地工具分支完成：旧作业含工具检查时仍须成功，新作业没有该步骤时继续要求精确提交核对和 Desktop 产品检查通过；日志证据只记录真实存在的步骤，缺席不伪造通过。手动及后台入口复用同一判定。
5. 保留原任务、独立目录、分支和 PR。0.5.4 已完成同源发布核对，固定入口切换和旧记录迁移已经完成，兼容读取已生效；持续审阅设置完成后重新提交本提案，当前提交的 GitHub 检查通过后自动审阅，通过即合入。测试账户的试运行按其原任务另行执行，不作为本提案提交的前置条件；它也不代替任何版本验收。本清理不改已发行的安装包或产品运行代码。
6. 产品提案使用登记入口，按已经启用的持续授权执行审阅，费用与轮数累计计入本 PR；本决策不新增或扩大预算，不逐材料开费用单。每次远端写入后回查结果，未知时先核对。这是新审阅流程的首次实际使用，遇到问题就停止并向开发者报告。

## 预期效果

产品仓库只承担产品代码和产品检查，本地工具由独立仓库维护。旧、新两种产品 CI 回执都可以按其真实步骤被正确读取，不因移除本地工具而降低产品检查要求。

## 考虑过的其他做法

继续保留旧副本会造成双重维护；只删目录不改 CI 会让检查失败；不满足准入条件就更换入口会破坏原有交付保护。使用临时入口或伪造工具检查成功会使审阅证据失真，均不采用。

## 验收标准

- 提案删除 tools/dev-workflow 和指定 CI 步骤，修正公开入口说明并添加本决策；另只补充已明确的安装包交付说明。没有产品运行代码、版本、安装配置或测试执行脚本改动。
- GitHub 当前提交的 Desktop checks 通过，仍实际执行精确提交核对和产品模拟检查；清理后不再执行被删目录的工具检查。
- 本地读取器的检查覆盖旧步骤成功、旧步骤失败、新步骤缺席、产品步骤缺失或失败及提交不匹配；仅前两种有效布局中的成功情况放行。
- 清理提案正式审阅和合入使用已获准且实际生效的兼容入口；持续授权仍核对单次、PR 累计、每日金额及轮数限制，检查或审阅未通过不能合入。
- 公开说明无失效工具入口链接、个人路径、真实对话或凭据；两包及其验收证据始终对应同一候选，历史失败不能被覆盖为成功。旧代码、旧决策及目录外完整补丁继续保留。

## 风险

当前发行工作与清理共享产品 main；需要保留发行候选的确定源码，避免把清理当成产品修补。旧入口曾无法接受缺少工具检查的 CI；本提案须继续通过已启用的兼容入口处理，不能从本地实现完成推断实际入口版本。兼容实现若把任意失败步骤当作缺席，会削弱检查，所以步骤存在但失败必须拒绝。历史说明保留其当时事实，不把历史链接当作现行执行入口。
