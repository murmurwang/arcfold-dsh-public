# 决策：从产品仓库移除本地维护的开发工具

## 来源

开发者已安排开发工具转入独立本地仓库维护，并在产品修复提案合入后清理公开目录及相应工具检查步骤。产品修复已合入，现登记本次清理的具体范围和交付顺序。

## 问题

产品仓库仍保留 tools/dev-workflow 下的工具源码，并在 Desktop 检查作业中运行它们的单元检查。工具已经转入本地仓库开发，继续保留旧副本会产生两个维护位置。移除目录后，原 CI 的工具检查步骤和公开 AGENTS.md 指向该目录的链接也需要同步处理。

当前安装的入口仍强制要求 CI 回执含“运行工作流检查”。只删除 GitHub 中的步骤，会导致该入口拒绝清理提案的审阅与合入。仅在本地完成兼容代码而尚未切换入口，不能解除这个实际限制。

## 方案

1. 从开工时实际 GitHub main 建立本任务的独立目录，删除 tools/dev-workflow 的 20 个受版本管理文件；合入前重新核对目录清单。
2. 仅删除 .github/workflows/desktop-checks.yml 的“运行工作流检查”步骤，保留 Desktop 作业名称、macos-15、精确提交核对、依赖安装及产品模拟检查。
3. 只调整公开 AGENTS.md 中指向被删目录的入口说明，明确开发工具独立维护，不加入本机路径、私人记录或对话；新增本任务决策说明。其他在途提案的工具目录外修改另行保留处理。
4. 本地工具的 CI 读取兼容在本地工具分支完成：旧作业含工具检查时仍须成功，新作业没有该步骤时继续要求精确提交核对和 Desktop 产品检查通过；日志证据只记录真实存在的步骤，缺席不伪造通过。手动及后台入口复用同一判定。
5. 现用入口按既定安排在 0.5.2 发布并获实际验收之后才能切换；本清理提案可以在方案对齐后准备、提交并运行 CI，但独立审阅与合入须等兼容读取已从获准的入口生效。清理不改变 0.5.2 已合入的源码或发行候选；发布与验收由其原交付继续。
6. 产品提案沿用现有决定、检查、审阅和合入流程。实际审阅材料和费用明确后再开按该 PR 累计金额绑定的授权单，本方案不授予付费请求权限。每次远端写入后回查结果，未知时先核对。

## 预期效果

产品仓库只承担产品代码和产品检查，本地工具由独立仓库维护。旧、新两种产品 CI 回执都可以按其真实步骤被正确读取，不因移除本地工具而降低产品检查要求。

## 考虑过的其他做法

继续保留旧副本会造成双重维护；只删目录不改 CI 会让检查失败；提前更换现用入口会违反已确认的产品发行与验收顺序。使用临时入口或伪造工具检查成功会使审阅证据失真，均不采用。

## 验收标准

- 提案只删除 tools/dev-workflow，删除指定 CI 步骤，修正公开入口失效说明并添加本决策；没有产品运行代码、版本、安装配置或其他在途改动。
- GitHub 当前提交的 Desktop checks 通过，仍实际执行精确提交核对和产品模拟检查；清理后不再执行被删目录的工具检查。
- 本地读取器的检查覆盖旧步骤成功、旧步骤失败、新步骤缺席、产品步骤缺失或失败及提交不匹配；仅前两种有效布局中的成功情况放行。
- 清理提案正式审阅和合入使用已获准且实际生效的兼容入口，付费授权绑定本 PR 累计上限；不提前切换现用工具或迁移旧记录。
- 公开说明无失效工具入口链接、个人路径、真实对话或凭据；旧代码和交付历史继续由 Git 与外部记录保留。

## 风险

当前发行工作与清理共享产品 main；需要保留发行候选的确定源码，避免把清理当成产品修补。旧入口无法接受缺少工具检查的 CI，这是明确的交付先后条件。兼容实现若把任意失败步骤当作缺席，会削弱检查，所以步骤存在但失败必须拒绝。历史说明保留其当时事实，不把历史链接当作现行执行入口。
