# 决策：兼容 0.4.x 升级时临时创建的旧模型连接

Status: proposed
observed_in_version: 0.5.3
fixed_in: 0.5.4
user_verified: pending

## 来源

F11：0.5.3 普通账户验收在升级确认时失败。0.4.1 安装、对话、预设失败恢复及 0.5.3 安装已通过；原包、草稿、界面与失败记录保留。

## 问题

根因：0.4.1 临时创建的旧模型连接没有对应的持久配置条目，DSH 原生插件管理入口拒绝修改它；0.5.3 因此中止启动。真实界面清单与原版 DSH 最小复现一致。之前检查把这个连接写进了配置文件，漏掉真实升级分支；本次网页导入正常，历史 F9 原因仍未确认。

## 方案

改法：对能对应持久配置的旧连接继续使用 DSH 原生保存；对确认属于 Arcfold、仅在运行时创建的旧连接，沿其原创建位置停用，并确认不再活动。随后持久保存新运行设置；遇到归属不明、冲突或无法停用仍停止，不改供应商密钥与模型列表。

按 A79 已选方案，使用现有 248c8b5 入口另开 PR，版本 0.5.4；0.5.3 验收失败不发布，草稿和原包保留。此次修复累计审阅预算仍不超过 1 美元，PR #35 已用 0.1938501 美元，新 PR 可用剩余 0.8061499 美元，修后再审沿用。审阅通过即合入，最终验收通过直接发布 GitHub/npm；新版本发布前继续冻结 #34 和入口切换。A79 已选择此版本和授权安排，并追加下列只读配置结构对比要求。

## 预期效果

从日常旧版更新后，一次确认即可启动原生模型途径，原会话和目标保留；配置刷新和完全重启后仍可使用。

## 考虑过的其他做法

不忽略停用失败，也不把报错后手动重启当作正常启用。保留 0.5.3 版本号需要先修改旧入口的同版本候选处理规则；本方案建议避免同时改动发布流程。

## 验收标准

- 最终验收前，只读对比日常 DSH 和测试账户的配置结构，包括安装的插件、模型连接及是否运行时创建；不读取密钥。日常环境有而测试账户没有的情况，补进预检。
- 先在付费审阅前用真实 0.4.1 原包跑完整升级、确认、首条原生消息、配置刷新和重启读回，再跑全新资料三项预验；回归检查按旧版实际方式临时创建连接，并覆盖持久连接及归属冲突。
- 检查和独立审阅通过后合入、双构建，最终原包重做普通账户完整验收；失败不改写为通过，需要本人操作时合并步骤。

## 风险

临时连接与持久条目必须准确区分，不能借兼容旧版改动其他插件。修补尚未实现，最终普通账户验收仍是发布条件。
