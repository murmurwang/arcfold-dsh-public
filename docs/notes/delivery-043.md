# 决策：[043-D1] PR 的 Desktop 检查拆成两路并行，缩短每次 CI 等待

Status: proposed
observed_in_version: 0.6.0
fixed_in: pending
user_verified: pending

## 来源

开发者在对话中提出 CI 太慢，要求给出兼顾效率与质量的精简方案，并回复“写决策”（2026-11-20）

## 问题

每个 PR 推送后要等 Desktop 检查跑完才能审阅和合入，一次要 9 分钟左右，有时还要先排队 5 到 16 分钟。四个 session 并行开发时，大家都在等这一步。

2026-11-16 到 11-20 的 30 次运行里，作业本身 8 到 10 分钟。准备环境和装依赖不到 1 分钟，其余都在“在独立副本运行 Desktop 模拟检查”这一步：1151 个测试，Node 报告 459 秒。按测试名归到文件，`test/tree-e2e.test.mjs` 一个文件约 246 秒，其中最长的两个测试分别 106 秒和 65 秒；第二慢的文件 `runtime-init.test.mjs` 约 45 秒。同一文件内的测试依次执行，macos-15 机器 3 核，`node --test` 默认同时跑 2 个文件，所以整次检查基本被 tree-e2e 拖住。

另外有同一分支 40 秒内推送两次、两次运行都跑完的情况（44549527863、44549642113），旧提交的结果没人再用。

这几天的 4 次失败都抓到了真问题，分别在 tree-e2e、目标修订原生测试和宿主契约测试里，所以问题是跑得慢，不是测试多余。

## 方案

不删测试，只改执行方式。

1. `.github/workflows/desktop-checks.yml` 的 Desktop checks 改成两路并行作业：一路只跑 `test/tree-e2e.test.mjs`，另一路跑其余全部 `test/*.test.mjs`。两路都保留现有的提交核对、计数环境校验、锁定依赖安装和独立副本运行，`scripts/test-isolated.mjs` 已支持传入文件列表，不改。第二路的文件列表在作业里由 `test/*.test.mjs` 去掉 tree-e2e 得到，以后新增的测试文件自动进第二路。
2. 加 `concurrency`，同一 PR 有新推送时取消还在跑的旧运行。手动触发（workflow_dispatch）不取消。
3. 前置条件：开发工具判断 CI 是否通过的读取（`workflow.py` 的 `completed_ci` 及相关审阅记录）目前只认一个叫 `Desktop checks` 的作业。要先在 dev 工具里改为：两路作业都必须存在且成功，每路都有成功的“核对检查使用的提交”和“在独立副本运行 Desktop 模拟检查”；任一路失败、取消、跳过或缺失都不算通过。旧的单作业布局继续按原规则读取。`workflow.py` 在受保护清单内，按规则经只读子 Agent 独立审阅、开批准单后 land，并启用入口后，本任务的 PR 才审阅合入。

## 预期效果

PR 推送后，从作业开始到出结果由 9 分钟左右降到约 5 到 6 分钟（tree-e2e 一路约 4 分钟加准备约 1.5 分钟）。连续推送时旧运行被取消，少占一个 macOS 名额。检查范围和现在完全相同。

这是按 11-20 日志估的，没有实际跑过。排队时间取决于 GitHub 的 macOS 机器，本方案不保证缩短。

## 考虑过的其他做法

- 把 tree-e2e 等慢测试移出 PR CI，只在发布候选时跑：最省时间，但最近的失败就有在这里抓到的，移走后问题会先进 main，后面所有任务都从坏的 main 开始。不采用。
- 拆成三路或更多：免费账号同时最多 5 个 macOS 作业，四个 PR 同时跑时路数越多排队越久，收益抵不过。先两路。
- 把 tree-e2e 里最长的两个测试拆到单独文件，让它们也并行：大约还能再省 1 分钟，但要改测试文件。先看两路的实际效果，不够再单开任务。
- 改用 Ubuntu 机器（更快、排队少）：检查用到 macOS 专用的计数环境和文件复制方式，换平台要另外核实，不在本次范围。
- 只跑与改动相关的测试：判断“相关”容易漏，且本地推送前已经这么做，CI 的作用正是全量兜底。不采用。

## 验收标准

- 本任务 PR 上的检查出现两路作业且都成功，两路测试数相加等于同一提交单路全量运行的测试数，没有被跳过的测试文件。
- 在测试中故意让任一路失败（或取消一路），开发工具的审阅和合入入口判定 CI 未通过；两路都成功时判定通过；旧的单作业运行记录仍能按原规则读取。
- 同一 PR 连续推送两次，较早那次运行显示已取消，最新提交的运行正常跑完。
- 合入后连续 3 个 PR 的检查，作业开始到结束不超过 7 分钟。超过时记为 fail，不改写成通过。

## 风险

- 开发工具读取没先更新就合入本 PR，之后所有 PR 都会被判“CI 未通过”而卡住。所以严格按方案第 3 条，先 land 并启用入口，再审阅合入本 PR。
- 两路各自复制依赖、构建 method-ui，总机器时间多一次准备（约 1.5 分钟）。公开仓库不收费。
- 取消旧运行后，如果有人恰好在等旧提交的结果，会看到“已取消”。审阅和合入只认当前 PR 头提交，不受影响。
- 估算基于单次日志，实际耗时可能有出入；验收按实际时间判。
