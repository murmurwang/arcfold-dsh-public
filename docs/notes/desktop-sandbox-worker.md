# 决策：[041-D2] 修复桌面版每轮开始时沙盒子进程启动即崩、本轮报 kill EPERM

Status: proposed
observed_in_version: 0.6.0
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F39（2026-11-20T09:17:42+00:00 登记）

## 问题

开发者在日常 DSH 0.6.0（桌面版 0.2.2-rc.1）里每发一轮消息，Arcfold 都会先给工作区拍一份快照，留着以后把文件恢复到这一轮之前的样子。桌面版里这一步从来没成功过。

原因：拍快照用的是最严格的那套沙盒（默认全禁，只放行指定路径），子进程用的程序是 DSH 主程序本身（Electron）。它启动时必须读 DSH.app 里的 Electron Framework，这套沙盒没放行，子进程一启动就被系统杀掉。

证据：Arcfold 自己的诊断记录里有 snapshot_unavailable，内容是读 Electron Framework 失败，几乎每轮一条；系统崩溃报告从 11-14 起约 49 份，时间和每轮开始对得上。本机复现：同一套沙盒规则，普通 node 正常运行，换成 DSH 主程序就崩。

现在的影响：失败被接住、只记诊断，不会让这一轮失败，但桌面版至今没存下任何一轮的快照，按轮恢复文件用不了，每轮还白白产生一份崩溃报告。

F39 里的 kill EPERM 原先推测也出自这里，开发时核对后没有证据支持：出错那一轮在拍快照之前就失败了，没留下快照诊断；在 DSH 环境里用 Arcfold 的沙盒起子进程，崩溃的和正常的各试了数百次，都没出现 EPERM。所以这份决策不再处理 kill EPERM，F39 保留，等再次出现时另查。

## 方案

只在桌面版、用 DSH 主程序当 Node 跑沙盒子进程时，把 DSH.app 的 Contents 目录加进只读放行（读和加载，不能写）。其他限制（网络、信号、私有资料、写入范围）都不变。目标树脚本用的也是这套沙盒，同样受益。

不改进程收尾的逻辑。

## 预期效果

每轮开始不再新增 DeepSeek Harness 崩溃报告和 snapshot_unavailable 诊断；桌面版开始真正存下每轮快照，按轮恢复文件可以用；目标树脚本在桌面版能跑。

这项不处理 kill EPERM（F39）、lmu 模型连不上或慢（F37、F38），也不处理每轮发请求前要等 60 到 100 秒的问题。快照以前从没跑通，修好后开始执行，会不会让每轮变慢，需要在验收里实测。

## 考虑过的其他做法

在沙盒里改用单独安装的 node：桌面版没有自带独立的 node，要求用户另装不合适。

把最严格的沙盒换成宽松的那套（默认放行）：能解决崩溃，但快照和脚本会失去默认全禁的保护，放弃。

原方案里的「收尾时 EPERM 当作已结束」：查不到 EPERM 出自这里，改了也未必修到用户看到的报错，还可能掩盖真正的进程问题，撤下。

## 风险

放行 DSH.app 的只读权限后，沙盒里的脚本能读到 DSH 程序文件本身。这些是公开的安装文件，不含用户资料；仍然不能写。

快照开始真正执行后，以前从没跑通过的快照和恢复逻辑可能暴露新问题，也可能拖慢每轮开始，靠现有快照测试和隔离验收兜底。
