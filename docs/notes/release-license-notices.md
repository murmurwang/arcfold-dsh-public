# 决策：补齐随包组件许可后发布原生模型配置版本

Status: proposed
observed_in_version: 0.5.0（已合入、未发布候选）
fixed_in: 0.5.1
user_verified: pending

## 来源

开发者明确要求「发布0.5.0」。发布前许可核查发现随包 Python 的精简归档缺少上游完整包列出的底层库许可，且旧分词 wheel 还需对照其依赖清单补足声明；对应独立审阅 Issue #17。版本选择待 A8 确认。

## 问题

用户安装 Arcfold 时同时取得包内的第三方程序，发行物需要保留对应的版权、许可和必要的源码取得说明。0.5.0 已通过两次相同构建与 npm 预演，但未发到 GitHub 或 npm。

对当前实际包核查发现：随包 Python 使用 Astral 的精简安装归档，保留了 CPython 和 pip 的许可，却没有上游同版本完整版在 PYTHON.json 中列出的 libffi、libedit、OpenSSL、ncurses 等底层库许可文件。完整版已取得，来源为 python-build-standalone 的 20260901 发行、CPython 3.12.14、Apple arm64。旧分词 wheel 内的 332 项依赖清单也需与现有许可文本逐项对应，不能仅凭有许可证名称就宣布核查完成。

另有一个已核实的发布约束：tools/dev-workflow/workflow.py 的 release_notes 要求修补版本高于当前 main 中的 0.5.0，confirm_merge 不允许把同一版本重新绑定其他提交。继续使用 0.5.0 需要先另行扩展未公开候选的修补流程；不能直接覆盖旧构建回执。

## 方案

建议修补后发布 0.5.1，保留 0.5.0 为未公开候选。

1. 根据已锁定的 Python 原包、分词 wheel 和依赖清单，从对应上游取得所需许可、版权声明及源码链接，写入 src/desktop/third-party/，记录原版本、来源和摘要。保留第三方原包字节，不修改模型调用行为、用户配置或历史数据。
2. 在实际发行包中核对这些材料确实存在，补充第三方组件说明；对无法核实的条目明确记录并继续处理，不记为通过。由 npm 另行下载的依赖与 Arcfold 自身再分发的组件分别说明。
3. 两份包、锁文件和更新说明统一为 0.5.1。重新运行适用检查、独立审阅、两次构建和隔离账户安装、失败恢复、更新、重启读回。独立审阅费用仍按新材料另行登记，不沿用 A5。
4. 完成后按发布授权推进 GitHub 和 npm。0.5.0 的源码、审阅和构建证据保留，不伪装为已经公开；0.5.1 包含原生模型配置功能及本次许可补齐。

## 预期效果

用户得到原生模型配置功能，以及与安装包一致、可追溯的第三方许可材料；修补不改变聊天或后台使用模型的方式。

## 考虑过的其他做法

保留版本号 0.5.0：可以做，但须先另开工作流任务，支持在核对 GitHub、npm 都未公开后保留旧记录并重新登记候选，再修补许可、审阅与验收。比直接采用 0.5.1 多一次工作流改动，因此不作为默认建议。最终版本由开发者决定。

直接发布当前包：已发现随包许可材料缺项，不建议跳过。移除全部旧计数资源：会另外改变安装包构成和旧模式兼容范围，本次不扩大到这个方向。

## 验收标准

- 当前随包 Python 的上游许可路径逐项有对应文件或明确的适用性证据。
- 分词 wheel 依赖的许可、版权及必要源码取得说明有逐项核对记录；未知项不得冒充通过。
- 最终核心包实际包含必要声明，界面包不误称打入了宿主提供的 React；保留的第三方归档摘要不变。
- 两份包、锁文件与更新说明均为已确认版本；自动检查、独立审阅和两次构建通过。
- 隔离账户验证原生模型设置、合成对话、失败恢复、更新及重启读回；日常 DSH 不被修改。
- GitHub 与 npm 公开下载逐字节对应验收原包，并核对发布信息不带个人本机路径。

## 风险

若上游资料不能覆盖某项再分发要求，发行仍需等待处理。工程核查只报告明确的材料与证据，不代替法律意见。采用 0.5.1 会跳过 0.5.0 的公开发行，但两者之间没有已公开用户需要迁移。真实模型效果和日常用户验收仍与隔离模拟分开记录。
