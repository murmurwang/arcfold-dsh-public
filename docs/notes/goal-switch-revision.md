# 决策：[075-D1] 主助手切换到已有目标时版本号对不上，切换被拒绝

Status: proposed
observed_in_version: 测试版 0.7.0（回放环境）；日常 0.8.0 同一段代码未变
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F51（2026-11-23T09:37:54+00:00 登记）

## 问题

测试版"我们继续写作品集文章"对话（会话 session-e34c8bb2，第 2 轮，模型 gpt-6.1-sol）。用户说"继续"，这一轮被归到根目标"我"。主助手判断应该接着已有目标"与 Murphy 逐段讨论、打磨第一篇文章，讨论到哪写到哪"，调用 arcfold_revise_goal，op 为 switch，nodeId 填这个目标，expectedRevision 填 14。工具返回 "Goal changed; read it again before revising"，主助手在回复末尾告诉用户切换被系统以目标已变更拒绝，这一轮归属没有改。

原因在 `src/tree/tools.mjs:106`：switch 时程序拿 expectedRevision 去比被切过去那个目标自己的版本（当时 90 左右）。但主助手拿到的材料里没有这个版本：编号表只有当前目标"我"的版本 14，全局概貌里每个目标只有 id、名字、一句话和上级，没有版本。主助手只能填 14，所以不管目标有没有变，switch 都必然失败。报错还让主助手以为是目标被改过，"重新读"也读不到版本。

日常 0.8.0 和当前 GitHub main 的这段代码相同，问题都在。

## 方案

switch 改为核对当前目标的版本，和"挪当前目标下面的目标"已有的做法一致：

1. op 为 switch 时，expectedRevision 须等于本轮某个当前目标（编号表 nodes 里的目标）的当前版本；对不上时报"当前目标已变化，用本轮编号表里的版本"。
2. 被切过去的目标不再核对版本。switch 不改这个目标的内容，只把本轮转过去；它是否还在、是否是候选，已有检查照旧。
3. 工具说明里 switch 一句补上"expectedRevision 填编号表里当前目标的版本"。

rename、create_child、add_parent、move 的核对不变。

## 预期效果

同样的调用（switch 到概貌里的已有目标，expectedRevision 填编号表里的当前版本）直接登记成功，本轮回答结束时转到那个目标，回复里说明切到了哪里。当前目标在本轮里真的被改过时，仍然会被拒绝。

## 考虑过的其他做法

- 在全局概貌里给每个目标加上版本号，让主助手填目标自己的版本。放弃原因：每轮都要多给一列数字，概貌一变缓存也跟着变；而且 switch 不改目标内容，核对它的版本防不住真正要防的情况。
- switch 完全不核对版本。放弃原因：当前目标在本轮被改过时应该让主助手重新看一眼，用当前目标的版本正好能防住。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

- switch 到候选目标、expectedRevision 填当前目标版本时登记成功，回答结束时本轮归到被切的目标。有测试。
- switch 时 expectedRevision 填被切目标自己的版本（与当前目标不同）被拒绝，报错写明用编号表里当前目标的版本。有测试。
- 当前目标在本轮已被改动后再 switch 仍被拒绝。有测试。
- switch 到非候选目标、已是当前目标、带不同名字时的原有拒绝不变；rename、create_child、add_parent、move 原有测试，以及 035、038、045、051、059、064 的修改目标测试全部通过。
- 日常观察（不作为发布条件，单独记录）：在新的日常或测试版里，新会话说"继续"某件已有的事，看主助手能否一次切过去、下一轮目标栏显示那个目标。

## 风险

- 一轮有多个当前目标时，填其中任何一个的版本都算通过，核对比原来宽一点；switch 本来就会把本轮所有当前目标换成被切的那个，影响有限。
- 合入后要重新做日常或测试版叠加，开发者才能看到效果；在那之前切换仍会失败。
