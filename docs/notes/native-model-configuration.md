# 决策：复用 DSH 原生模型配置并统一 Arcfold 各环节的聊天模型选择

Status: proposed
observed_in_version: 0.4.1
fixed_in: 0.5.0
user_verified: pending

## 来源

开发者在已展示的模型配置讨论方案之后明确要求：把这个模型配置途径问题开一个pr 配上决策文档 然后开始开发。

## 问题

用户在 DSH 的模型设置页配置模型，并在聊天输入框选择模型，希望 Arcfold 所有运行环节都沿用这一选择。0.4.1 保留了 DSH 原生设置页和选模器，却禁用原生模型连接插件、添加专用 DeepSeek 密钥表单；目标树运行时还限制 DeepSeek 的请求、输入计数和费用记录。后台已有来源模型继承，但思考强度仍按角色固定。因此，仅恢复设置界面会出现模型可选而后台拒绝调用的情况。

源码依据为 cordis.patch.yml、packages/method-ui/src/client.mjs、src/desktop/provider.mjs、src/tree/runtime.mjs、src/tree/model-owner.mjs 和 src/tree/token-counter.mjs。讨论只核对源码，未证明任意模型的实际效果。

## 方案

沿用此前已展示的方案：

1. 模型服务商、密钥、连接地址、可选模型及聊天选模使用 DSH 原生机制。Arcfold 不另建模型设置页或目录，不复制密钥，不改写用户的默认模型选择。
2. 发送一轮消息时记录该会话的有效模型选择。目标归属、主回答，以及由该轮引出的学习、整理、检验、改进和脚本编写都沿用它；模型和思考强度一起继承。下一轮的新选择不改变已登记任务；不同聊天之间不串用。跨多轮任务记录其来源任务的选择。
3. Arcfold 保留各环节的提示词、输入材料、工具权限、输出上限、结果来源和版本核对。复用 DSH 的模型执行流程，不增设另一套模型循环。取消 Desktop 对固定 DeepSeek 连接、价格表和专用计数器的依赖，按所选模型的能力处理输入和参数。
4. 每次调用记录实际服务商、模型、可获得的用量及结果状态。缺失用量或价格时明确记为未知，不伪造零费用、精确计数或结算成功；结果未知不自动重发。不支持的能力明确报告，不静默换用其他模型。
5. 保留既有数据和凭据，隔离验证首次使用、旧配置兼容和重启。开发仅使用合成资料与本机模拟模型；本决策不授权付费模型实验、改动日常安装、合入或发布。候选版本为 0.5.0。

## 预期效果

用户只需在 DSH 设置模型、在聊天中选择一次。Arcfold 全流程沿用该轮选择，模型配置与调用记录可以相互核对；更换服务商不再要求维护 Arcfold 专用模型目录。

## 考虑过的其他做法

只恢复设置页不能解除后台的 DeepSeek 限制，因此不采用。每次后台调用都读取全局最新选择会使已经排队的任务或另一段聊天串用模型，因此采用按来源记录的选择。继续扩充 Arcfold 专用目录会造成两套配置，因此复用 DSH 原生目录。

## 验收标准

- 原生模型设置页和模型列表可用，移除 Arcfold 专用密钥表单；凭据继续由 DSH 保存，测试与记录不泄露密钥。
- 合成环境中至少两种服务商及不同模型通过原生连接完成目标归属、主回答和后台学习，其他角色的模型继承与结果处理有对应检查。
- 模型、思考强度、延后执行、多聊天并行和重启恢复均保持来源选择；不得悄悄回退其他模型或读取另一个聊天的最新选择。
- 结构化结果的格式、来源、版本和工具权限核对仍有效；不支持的能力与未知请求明确记录，不自动重发。
- 用量存在、用量缺失、价格缺失、取消、错误及部分输出各自保留真实状态，不能把未知写成零费用或伪造结算成功。
- 旧版对话与目标保持可读；配置兼容、首次使用和原生模型设置交互在隔离环境检查，不直接修改体验环境。
- 两份包、锁文件和更新说明统一为候选 0.5.0；适用的离线检查通过，真实模型效果与本人验收仍标为未验证。

## 风险

统一使用较慢或较贵的模型会影响前置判断及后台工作的耗时和费用；不同服务商支持的思考参数、工具调用、输入长度、用量字段和结构化输出质量不同，列表可见不等于所有能力已验证。工程需覆盖这些差异并明确失败，不能宣称所有模型已经实测。旧的 DeepSeek 计费授权不能被当作其他服务商已经实际获准消费的证据；实际使用仍遵循用户在 DSH 中的设置与明确授权。
