## 来源

开发者要求在现有 dev 基础上设计修改方案：“让能并行的步骤尽可能并行，不得已的环节才串行，保证效率”。关联反馈 F4：已确认的候选修补任务，因为方案写了等待交付编号改造合入，整项编码尚未开始。

本次登记的是待确认方案。确认前不启动开发、不改变其他任务的已确认决定；原始观察及截图留在本机。

## 问题

当前不同任务已有独立源码目录，但进度仍把整项任务归为一个阶段，不能表达“其中一些步骤现在可做，另一些步骤等待前置结果”。Agent 因而容易把局部依赖写成整项等待。工具与文字也会矛盾：A9 的方案要求等 PR #18，当前 `next` 却显示可以 `start`。

源码另有四处放大等待：`submit` 要求任务起点等于当前主线；`release` 从安装依赖、两次构建到上传发行都占用与合入相同的锁，并要求主线始终不前进；GitHub 的 Desktop 检查与工作流检查在一个作业中先后运行；`release_notes` 要求每项插件改动都递增共享版本并修改两份包、锁文件及更新说明。这些限制阻止准备工作并行，或使独立任务争用同一套发行信息。

必须保留的约束来自具体对象：使用另一项工作的真实结果，需要先得到结果；同一主线、同一发布对象、同一测试资料不能被两个执行者同时改写；现有灵眸扣费核对要求一把密钥恰好只增加一次请求，因此同密钥发送到对账完成仍需排队。代码文件不重叠，不能单独证明两项行为相容。

依据为实际入口提交 `248c8b5` 的 `workflow.py:start/submit/material/review/merge/verify_receipt`、`release.py:prepare/release`、`collab.py:task_progress`、`common.py:locked`、`desktop_review_request.py:request/relay_bill`，以及 `.github/workflows/desktop-checks.yml`。实际审阅提示词仍要求以固定源码与检查证据逐项判断，关键项未知不能放行。本次也核对了未合入的 PR #18 `d39c3b6` 和审阅自动化草案；它们不作为已经启用的能力。

## 方案

### 1. 只让真正依赖的步骤等待

保留现有登记、决策确认、独立目录、提交、审阅、合入、发行和体验反馈。每项任务在这些阶段内列出可执行步骤，分别记录：需要什么输入、产出什么结果、依赖谁的哪项结果、会修改哪个共享对象、所需授权和实际完成证据。

依赖必须说明“缺哪项结果，以及缺它为什么无法做这一步”。默认只阻塞使用该结果的步骤。源文件范围重叠先提示组合风险，不自动阻塞开工；已确认范围内的内部拆分无需再请开发者决定。产品范围、对外后果或已确认方案中的明确等待条款变化，仍以新决策登记。

所有正式任务仍从启动时的 GitHub main 建自己的目录。依赖另一项未合入代码时，可以在额外的临时目录中组合其明确提交，验证双方如何衔接；上游提交变化后只重做受影响的组合检查。该结果不等于正式主线验收，也不使上游代码自动获得合入许可。

`next` 同时显示“现在可做、正在执行、具体等待、失败或结果未知”，写出等待对象、解除条件、已有证据和下一步。等待一条分支不能覆盖其他可执行步骤；登记依赖时拒绝循环，并指出由哪些步骤构成。`next` 保持只读；统一入口负责步骤领取和结果登记，编码仍由 Agent 执行，确定的检查与构建命令由并行执行程序运行，付费审阅交给已有受管路径或获准后的 A13 执行程序。完成一步后重新计算受影响步骤是否就绪，已在线的执行者继续处理原授权范围内的工作，不再要求开发者重复说“继续”；不据此承诺没有执行者在线时也能自动编码。

### 2. 并行范围与必须串行的边界

| 工作 | 并行安排 | 必须先后进行的部分 |
|---|---|---|
| 不同任务的方案、源码和本地检查 | 各自目录同时推进 | 本项实现以对应决策确认为前提；同一目录不交给多个执行者改写 |
| 提交草稿、自动检查、准备审阅材料 | 使用各自登记的固定源码同时准备；主线前进不禁止草稿提交 | 正式合入前须完成与当前主线组合后的检查和独立审阅 |
| 独立模型审阅 | 材料、估算和授权核对并行；计量与额度确实独立的不同专用密钥可分别执行 | 当前按同一密钥的累计用量差结算，发送至对账完成一次一条；不能只按提案分别加锁 |
| 合入主线 | 合入前的准备继续并行 | 一次完成一个主线写入及结果核对；结果未知时暂停后续主线写入 |
| 插件版本与更新说明 | 每项任务独立保存改动说明，先作为待发行源码交付 | 准备发行候选时统一确定版本、两份包及汇总说明；多个任务不各自抢改共享版本 |
| 构建和复建 | 对固定源码在两个独立构建目录运行，两次构建也可同时进行 | 两次都完成后才比较产物并登记通过 |
| 安装和更新验收 | 独立资料目录、端口和应用实例的测试可并行 | 同一测试实例的安装、对话、更新恢复及重启读回按真实状态转换顺序执行 |
| GitHub 和 npm 发行 | 构建、许可核对、附件准备、不同隔离环境验收与其他开发并行 | 同一版本的候选选择和对外写入、同一组包的默认更新指向需互斥；依赖包先可用后发布依赖它的包 |
| 编号、历史追加、步骤领取 | 内容准备和计算并行 | 只在分配编号或提交状态变更的短时间内互斥 |
| 切换正式 dev 入口及记录格式迁移 | 新旧格式兼容检查可预先完成 | 暂停接收不兼容写入，等已有写入核清，再切换；读查询和独立源码工作继续 |

表中的串行以对象为范围，不扩大到整个仓库或全部任务。缺少独立测试实例时只排队该环境；不为提速自动修改日常 DSH 或创建新费用来源。

### 3. 长计算与共享状态写入分开

每个步骤先在短暂的互斥保护下登记“谁领取了哪组固定输入”，然后释放记录锁，在自己的目录计算。完成后核对输入和执行身份仍相符，再追加结果。这种防止同时改写同一记录的机制称为锁。

运行记录保存源码及依赖的内容身份、所用工具版本、执行者、开始时间、结果位置、授权和恢复信息。普通记录锁不跨下载、测试或模型等待持有；但同一发布对象或审阅密钥的占用仍持续到实际结果核清，不因文件锁释放或等待超时而解除。

重复领取同一输入只能得到已有执行记录。进程退出后区分“尚未发送”“已发出但结果未知”“结果已保存”；未知结果先查询原对象，不能自动重发。旧进程迟到的结果保留为历史，不能覆盖新输入的状态。多对象操作采用固定的取得顺序，避免互相等待。

本期仍以同一套本机状态和统一执行入口为协调边界。多个聊天或进程可以共用它；不把本机文件锁说成跨机器保护。主线写入继续依赖 GitHub 的严格最新主线检查和禁止强推规则，并核对最终代码与父提交；其他入口造成竞争时停止相关写入并核对。本次读取到的仓库设置已开启严格 `Desktop checks` 和管理员约束，无需先修改远端权限。

### 4. 提前准备，保留最终组合验证

一旦提交的源码、依赖、命令、工具及环境确定，就保存一份固定输入记录，检查只证明这一组输入。其他任务向主线提交新代码，不会抹掉已有证据；只有实际输入变化的步骤才需要重做。

`submit` 将“可以上传草稿并运行检查”与“可以合入主线”分开。登记起点仍必须是已确认的主线历史，不能冒充已经包含最新改动。审阅材料也可提前准备，但默认在真实上游依赖落实、组合源码和检查稳定后再发起付费终审，减少必然失效的调用。

正式合入保留当前的严格条件：候选包含当时主线；检查和独立审阅对应同一候选、起点及材料；权限有效。A 先合入后，B 如需重新组合，新的代码组合必须重新检查并取得适用的独立审阅。旧报告作为旧源码证据保留，不由实现者判断“文件不重叠”就自动转成新组合的放行。仅重复读取同一份已完成证据不再重复执行。

合入队列选择前置已满足的候选，记录排队原因，并让等待较久的候选获得机会。它只在实际主线写入和核对时占用主线操作，不在测试、费用审批或模型运行期间长期占住主线。当前审阅证据规则下，主线变化仍可能要求补做最终组合验证；本方案不承诺消灭这一成本，也不引入绕过验证的合入通道。

### 5. 发布固定的已合入候选，让后续开发继续

先分开“源码改动已合入”和“已组成可发行版本”。新流程下，插件任务必须明确标记需要发行，并保存自己的改动说明，但可以先以待发行状态合入，不再强制每项独立功能都递增两份包版本。工具把纯 dev 改动与插件待发行改动分开判断，不能仅凭 `fixed_in: pending` 将后者误判为不需发行或已闭环。

准备发行时，从已受管合入的源码明确列出本次包含的任务和审阅，另用一项范围很小的发行组装改动统一确定版本、两份包信息、锁文件和更新说明。该改动仍经过正式组合检查、独立审阅和受管合入，然后登记候选；不把原任务的通过结论直接拼成发行放行。选中的源码实际包含哪些改动，就必须完整列出哪些改动；不能只挑清单而把源码中其他变化隐去。版本分配与目标选择短时互斥，禁止多个组装任务争用同一目标；未被选入本次源码的后续工作继续开发。已登记的同版本修补仍引用原候选，不能借“待发行”绕过已发布版本不可换包的约束。

发布目标改为“明确选中的一次候选”：固定的已合入源码、两份包、构建输入、审阅、验收及授权。它一经登记，后续主线前进不要求重新选择源码，也不取消正在进行的构建。

候选必须有受管合入回执，源码仍属于主线历史，未被替代或撤销，整组包和实际验收对应同一次候选。不能临时挑任意历史提交发布；不能悄悄换成最新源码。新修补产生新的候选，旧产物与失败记录保留。候选选择、替代与发布检查使用同一版本的互斥保护，避免一边替代一边发布。

移除构建、复建及隔离验收对主线操作的长期占用。发布前仍查 GitHub、npm 和本机未知操作；同一版本开始对外写入后锁定内容，两份包部分成功时只恢复同一候选剩余的步骤。默认更新版本不能被较旧任务改回去；同一组包的正式发布协调默认更新指向，无法单独核对的操作按组排队。

早于正式合入的试构建可以提前发现问题，但正式发行仍需对应受管合入源码的构建与验收。两次正式构建从同一固定输入出发，各有源码副本、可写依赖目录和输出；不能把复制第一次产物当作复建。只有校验过的下载内容可以只读共用，任何缓存填充也按内容单独协调。

### 6. 自动检查与本机资源一起调整

把 GitHub 的 Desktop 检查和 dev 工作流检查拆成独立作业，各自取得并证明同一个源码提交；最后由仍叫 `Desktop checks` 的汇总作业核对全部必需结果。缺失、取消、跳过或失败都不能汇总成通过。同步修改正式审阅入口，使其核对每项实际作业、日志与提交，不能只信汇总名称。

上线顺序必须是“先合入并启用可识别新旧真实回执的入口，再切换检查布局”。兼容入口仍接受原来的真实检查；拆分工作先在独立分支验证，不伪造旧作业的步骤或日志。这是依赖新读取能力的局部串行，不要求其他开发等待。

本机重计算默认最多同时两个步骤，占用同一执行池，子进程也计入限制；不要每个任务各自开启无限测试进程。不同任务共享经过校验的只读下载输入，各自写输出。优先运行能解除后续等待的步骤，同时防止长任务一直被插队。并发上限可按实测调整，不以“进程越多”判断效率。

### 7. 与 A9、A13 和 PR #18 的衔接

PR #18 是编号和历史归属的实现来源。若尚未合入，本任务先按当前 main 开工，通过一个集中处理旧、新记录读写的适配层开发；编号接入与旧记录迁移才等待正式新入口。不得复制出第二套编号分配器，也不得等待 PR #18 才开始所有工作。新编号要求变化时只修改集中接入处，并重验相关步骤。

本方案要求对 A9 的已确认文本做三处明确修订，正式登记时保留原决定与确认：

1. 第 7 条中的“等交付编号改造合入后，本任务从当时主分支开独立目录”改为：“本任务从启动时主分支开独立目录；候选保存、修补判定和模拟检查先行，交付编号接入及正式组合验证等待编号改造的适用结果，不能以此阻塞无关步骤。”
2. 第 3 条中的“主分支前进时仍沿用现有暂停核对规则”改为：“主分支前进不取消已登记且仍有效的发行候选；继续核对候选的受管合入来源、未被替代、整组包与授权一致。候选变更、被撤销或存在结果未知的对外写入时，暂停受影响的步骤。”
3. 第 1 条中的“合入时即登记候选”细化为：“普通插件源码交付合入后登记为待发行；统一发行信息的改动合入后，登记包含明确任务清单和版本的候选。已登记候选的同版本修补继续明确引用原候选，合入后追加新候选。”

这三项是对原方案的实质调整，不能沿用旧文本的确认冒充已经批准。旧 0.5.0 历史及 A8 已决定的 0.5.1 交付安排不因此改变；已按旧流程登记的发行继续识别原回执，新规则用于显式启用后的交付，不回写已有版本归属。

A13 仍负责批准之后的密钥读取、审阅执行和对账；本方案只统一步骤准备、资源占用和进度。共用一套审阅执行记录，不另建常驻审阅程序，不由本方案启用新的密钥保存方式或放宽费用授权。其当前同密钥串行安排保留，材料准备并行。未批准的审阅只等待授权，其他无关步骤继续。

### 8. 实施和上线安排

先约定步骤输入、完成证据及共享对象的读写格式。随后三组实现可以各在独立源码副本推进：步骤依赖与 `next`；执行记录、短锁与恢复；检查拆分及构建目录隔离。候选发布的修改由 A9 的候选记录实现承载，按上述修订与本方案接合，不让两个任务各维护一套发布历史。

组合时根据明确的接口检查各自结果。同一入口文件由负责组合的执行者落入主任务工作目录，避免两个进程同时改工作区。兼容读取能力先上线，检查布局及记录写入方式随后切换；候选记录准备好后再启用脱离当前主线位置的发行。各项已完成且独立的改动可以先提交审阅，不等整套方案一起完成。

本次改动限于登记范围内的 dev 工具、自动检查和说明，不因此增加插件版本。后续具体实现按现有新决策与独立任务规则登记，复用本次明确确认的范围和原话，不能扩大授权。源码审阅、公开合入、安装执行程序、真实模型费用和用户环境动作仍核对各自实际授权。旧任务原文不在本次起草阶段改写。

## 预期效果

开发者可以同时推进多个独立问题，并直接看到每项任务中现在能做什么。构建中的发行不会阻塞主线合入，等待一次批准或一个测试实例不会让其他任务空转。每一处等待都能追到所需输入或具体共享对象；新代码、安装包和实际验收仍有对应证据。

记录每步运行时长、等待时长与原因、实际并发数、重复检查次数和模型实际费用。在相同工作量下比较串行与并行安排，以端到端完成时间和返工为准；实施前不宣称已经提速。

## 考虑过的其他做法

只改 Agent 提示为“尽量并行”，无法消除 `release` 的主线锁和 `next` 的单一阶段表达。去掉所有锁，会造成重复请求、记录覆盖及包版本竞争。按文件不重叠自动沿用旧审阅，无法覆盖跨文件行为依赖。一次建立跨机器调度与自动批量合入，改变范围过大；本期复用现有本机入口、GitHub 检查和 A13 执行路径，把等待缩到可核对的步骤和对象。

## 验收标准

- 两个互不依赖的任务可从各自目录同时开发、提交草稿和检查；其中一个等待审批或前置合入时，另一个仍能推进，`next` 同时列出可做与等待步骤。
- 给一个任务登记局部上游依赖后，仅消费该结果的步骤等待；拒绝循环依赖，并能展示等待来源、解除证据与仍可执行的工作。
- 使用受控的并发执行检查证明两个独立步骤确实重叠运行；同一输入只领取一次，同一共享对象不会出现两个有效写入者；运行输入变化后旧结果不能覆盖新状态。
- 模拟进程退出、超时、迟到结果及远端已成功但本机未确认，均按原对象恢复，不重复模型请求、合入或发布；未知操作只阻塞相关对象及其依赖。
- 主线在构建期间前进，原已合入且仍有效的候选可以继续构建和验收；候选被替代、来源被移出主线、包内容变化或授权不符时拒绝发布。
- 两项插件功能可各自合入为待发行而不争用版本号；发行组装完整列出选定源码包含的任务，统一两份包、锁文件和说明，缺少任一来源审阅或最终组合证据时拒绝；待发行不得显示为已发布或已验收。
- 两次构建在不同可写目录完成并逐字节比较；检查缓存只读复用与内容校验，覆盖同版本旧缓存、同名输出及不同依赖版本相互污染的情况。
- 新旧自动检查回执均可定位真实作业和源码；缺少任一必需结果时阻塞；先部署兼容读取再切换检查布局的过程可在本地模拟和 GitHub 检查中验证。
- 同一专用审阅密钥从发送至费用核清保持独占，不同有效且独立计量的密钥才允许并发；无授权时发送次数为零，不增加预算或自动换服务。
- 合入继续核对最终候选与当前主线对应的检查和独立审阅；文件不重叠、旧报告通过或本地模拟成功均不能替代新组合所需的证据。
- 发行部分成功、默认更新版本竞争、入口切换和旧记录迁移可恢复且保留原证据；日常安装、配置、凭据及数据无未经授权的写入。
- 对同一批独立任务记录串行与并行的完整耗时、等待原因及执行次数，确认减少了跨任务等待；若资源争用使实际完成更慢，调整并发上限后再验收，不以启动数量宣称有效。

## 风险

步骤记录会增加恢复与兼容工作；因此复用现有交付、请求和审阅身份，只新增执行关系，不另发一套面向开发者的材料编号。所有迁移保留旧文件与失败记录，切换失败可恢复旧入口，但不得让旧程序写入它不认识的新记录。

主线持续前进仍可能使最终组合验证需要重做；在保持当前独立审阅绑定规则的范围内，不能承诺完全消除。并发可能增加内存、磁盘和远端检查开销，必须按实际完成时间调整。外部写入、共享密钥被其他程序使用及跨机器执行，不能仅靠本机锁保证；遇到无法核对的竞争，应缩小暂停范围并报告实际原因。
