# 决策：[085-D1] 数据多了启动、读历史和回答都变慢

Status: proposed
observed_in_version: 0.8.0 预览（第 4 次候选），测试版装 main
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F56（2026-11-23 登记，附 4 张截图）。Murphy 原话：两个都开。专项结论见 requests/f56-speed/findings.md。

## 问题

Murphy 在测试版里感觉什么都慢：启动要等很久；点开会话长时间停在「载入历史...」；Arcfold 页签点一个目标，右边一直「正在读取...」；发了消息按钮转很久才开始回答。

实测：
- 启动计时里 `recover-replay-committed` 一步，测试版最近几次 36s、70s、74s、167s、110s、125s；日常同一步 1.6s。
- 测试版目标树 15055 条记录、85MB，其中后台任务记录 `tree_jobs` 420 条共 47MB，最大一条 3.3MB（整理任务把完整提示存在记录里）。日常 2006 条、8.6MB。
- `repo.list('tree_jobs')` 每次都把整张表读出来逐条 JSON 解析，测试版一次约 1.2 秒，日常约 0.1 秒。代码里有 39 处这样的整表读。后台扫描 `scanOne` 每次至少读 5 遍，每轮结束、每个后台任务结束、每 60 秒都会触发；主对话每次请求的 `mainJob` 也读一遍。
- node:sqlite 是同步调用，读的时候 DSH 主进程别的事都做不了。测试版主进程常驻 80～90% CPU，采样热点都在 sqlite 读取。界面的历史、目标详情和流式回答都在排队等它。

这不是测试版独有：代码和 0.8.0 一样，耗时跟着数据量涨。日常现在每次扫描大约 0.7 秒，再用几周会走到测试版现在的样子。

## 方案

1. 在 repository 里给 `tree_jobs` 加一份轻量索引：只用 `json_extract` 取 id、role、kind、status、nodeIds、trigger 里的会话和轮次、enqueuedOrder 这些筛选要用的字段，按 SQLite 的 data_version 失效，自己写入时同步更新。做法和现有 `listByNodeIds` 的内存索引一致，不改磁盘结构。
2. 扫描、恢复、`mainJob`、`queued()` 等热路径改成先在轻量索引里筛，只对筛中的几条读完整记录。不在热路径上的少数整表读保持不变。
3. `scanOne` 里多次筛选合并成一次读取。
4. 启动计时和后台扫描各记一次耗时，写进现有诊断记录，方便以后看到数据量变大时的趋势。

## 预期效果

- 用测试版这份数据：启动里 Arcfold 的恢复步骤从两分钟降到几秒以内；一次后台扫描从几秒降到 0.1 秒量级。
- 载入历史、读目标详情、开始回答不再被后台扫描卡住。
- 行为不变：哪些任务被恢复、排队、执行，和改之前完全一致。

## 考虑过的其他做法

- 加 SQLite 表达式索引：要改磁盘结构，旧版本回退时有兼容问题，先不做。
- 把整个 Arcfold 后台挪到独立进程：改动太大，而且不解决重复整表读本身。
- 定期清理旧的已完成任务记录：会丢掉审计和回放需要的历史，不做。
- 不再在任务记录里存完整提示：能减小体积，但牵涉记录格式和回放，单独评估，不放在这次。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。
- 用测试版目标树的同等规模合成数据（约 420 条任务、47MB）：启动恢复步骤 < 5 秒，一次 `scanOne` < 200 毫秒，扫描路径上不再整表解析 `tree_jobs`（测试里计数）。
- 现有恢复、排队、学习、整理、检验相关测试全部通过，结果与改动前一致。
- 别的连接写入后，轻量索引能读到新状态（data_version 失效测试）。

## 风险

- 轻量索引和真实记录不同步会导致任务漏跑或重复跑。缓解：失效规则沿用现有 `listByNodeIds` 已验证的做法，并加并发写入测试。
- 本机负载高时数字会比验收环境差，验收以同一台机器改动前后对比为准。
