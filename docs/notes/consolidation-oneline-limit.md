# 决策：[062-D1] 整理的一句概况超过 60 字，整次结果作废

Status: proposed
observed_in_version: 0.7.0 + main@8b432a6（测试版）
fixed_in: pending
user_verified: pending

## 来源

Agent 查看测试版目标树记录里的后台调用用量时发现。Murphy 原话：draft 2345

## 问题

<!-- 谁在什么场景遇到什么，实际发生了什么，证据在哪里。一份决策只写一个问题。 -->
整理的输出规格要求 `summary.oneLine` 不超过 60 字（`src/tree/prompts.mjs:24`，`str(60)`），超过就判不合格。现在整理用的是精简版提示（`arcfold.tree.consolidation/5.0.0`），格式说明里只写了 `"oneLine":"一句概况"`（`prompts.mjs:558`），没写字数上限。完整版提示后面附了整份 JSON 规格，模型能看到 60 字；精简版没附，模型不知道有这条限制。

摘要是整理的基本单位，摘要不合格整次就作废（`prompts.mjs:387`），不会只丢掉 oneLine 留下其余部分。

### 实际例子

- 2026-11-21 14:13，一个目标离开后触发整理。模型写的 oneLine 有 89 字，整份结果判为 INVALID_OUTPUT（`$.summary.oneLine`，字数超限）。这次调用花了 94,480 输入 token，没有留下任何结果。
- 当前测试版目标树记录里，到现在一份摘要都没有，所以目标概貌里每个目标的一句概况都是空的。
- 同样的材料不会再整理一次（同一目标、同一批轮次、同一原因的任务只建一次）。要等这个目标有了新的轮次，下一次整理才可能成功。
- 主对话的压缩也走整理环节、用同一份提示（`src/tree/runtime.mjs:589`）。oneLine 超长时压缩同样失败，对话保留原来的历史，不压缩。

## 方案

1. 精简版整理提示里写明上限：格式说明改成 `"oneLine":"一句概况，60字以内"`；开头说明整理要保留什么的那段，补一句"oneLine 是 60 字以内的一句话"。
2. 提示版本号升一位。已经冻结的旧任务保留原来的提示，不受影响。
3. 校验规则不变，仍是 60 字。

## 预期效果

- 整理和主对话压缩不再因为 oneLine 超长整次作废。
- 目标概貌里开始出现各目标的一句概况。
- 不改其他输出要求，不增加调用次数。

## 考虑过的其他做法

<!-- 只写真实考虑过的做法和放弃的原因。 -->
- 程序把超长的 oneLine 截到 60 字：改了模型写的内容，截断可能断在半句；校验规则也要改，不采用。
- 超限时发一个很短的修复请求，只让模型重写 oneLine：能兜底，但要多一种请求和用量记录。先看写明上限之后还会不会超。
- 把上限放宽到 120 字：每轮主对话的目标概貌都带每个目标的 oneLine，变长会让每轮背景都变大。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

## 风险

- 写明上限也不能保证模型每次都遵守。回放里还超的话，再考虑修复请求。
- 14:13 那次失败不会因为这次修改重跑，要等那个目标有新的轮次。
