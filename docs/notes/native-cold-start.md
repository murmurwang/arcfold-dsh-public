# 决策：修复原生模型版本重启时的运行代码加载冲突

Status: proposed
observed_in_version: 0.5.1（已构建、有 GitHub 标签和草稿、未公开发行）
fixed_in: 0.5.2
user_verified: pending

## 来源

0.5.1 隔离验收发现：原版 DSH 0.2.2-rc.1 完全重启后 Arcfold 核心组件加载失败，导致会话不可用；A21 继续入口已实际复现。用户要求继续完成发行，具体修补方案与 0.5.2 版本选择待对齐。

## 问题

用户完成原生模型设置并退出 DSH 后，再打开应能继续使用原会话。0.5.1 在普通账户的实际测试中，安装、合成对话、下载失败恢复和更新均已完成，但完全重启后 Arcfold 核心组件加载失败，会话服务不可用；刷新插件暂时恢复，再次完全重启仍失败。

已取得错误栈和加载记录：Arcfold 在核心组件启动后才临时导入树运行代码；DSH 0.2.2-rc.1 同时进行启动后的插件刷新，把尚未完成加载的 undici 依赖当作失败项清除。Node 随后发现加载记录不一致，报 ERR_INTERNAL_ASSERTION。不是模型请求失败。

独立小复现使用原签名应用中的 Electron、DSH 插件刷新机制和原 0.5.1 运行代码。在控制启动时序并禁止外发网络的条件下，原加载方式连续三次失败；提前加载连续三次通过。这仅验证修复方向，不代替修改后整包的实际验收。

## 方案

1. 在 Arcfold 核心组件被读取时完成运行代码的导入，再按现有设置与确认记录决定是否启动。只调整加载时机；保持聊天模型选择、旧设置保护和未经确认不启动流程的规则。
2. 增加真实 DSH 刷新机制参与的回归检查，验证重启时不会清除正在导入的依赖，并核对未初始化与旧模式入口。原版 DSH 应用不打补丁，日常环境不改动。
3. 建议修补版为 0.5.2。0.5.1 已存在 GitHub 标签及发行草稿，现行入口不允许换包；另一个已对齐的未发布候选修补方案也明确排除了已有标签或草稿的情况。保留 0.5.1 的原包、失败及审阅证据，不把它正式发行。
4. 新代码重新提交 PR，完成检查、独立审阅和两次构建；再用新原包完成隔离账户安装、失败恢复、更新、完全重启读回、原生模型设置及两种聊天模型的合成验收，通过后完成 GitHub/npm 发布。付费独立审阅另行登记，不把旧回执用于新源码。

## 预期效果

用户更新后完全退出并重开 DSH，原会话和目标仍可读，Arcfold 自动启动；不需要手动刷新插件来恢复。

## 考虑过的其他做法

继续发布现有 0.5.1：重启失败已重复出现，不满足发行验收。

保持 0.5.1 但更换草稿与标签：需要重新决定是否允许替换已写入 GitHub 的版本，并扩展正在开发的候选修补流程。本次建议先采用现有流程能完整保留证据的 0.5.2。

要求用户每次重启后刷新插件，或改动宿主关闭自动刷新：增加日常操作或改变 DSH 自身行为，不符合正常安装即用的目标。

## 验收标准

- 回归检查先证明原实现可复现该冲突，再证明修补实现通过；关键加载与未经确认不启动的规则均有检查。
- 适用的产品、打包、许可和工作流检查通过；独立审阅绑定新提交，两次构建产物相同。
- 隔离账户从正式旧版安装，经下载失败恢复和成功更新后，完全退出重开能读回同一会话、目标和来源；读回不增加模型请求。
- 全新资料使用 DSH 原生设置与聊天模型列表，两种模型的主回答和实际观察到的后台调用对应来源轮次；使用本机合成服务，不扩展成真实模型效果证明。
- GitHub/npm 的正式安装包与最终验收包一致；0.5.1 的失败记录继续可查。

## 风险

提前导入会让尚未启用树流程的入口也先读取运行代码，因此需要检查首次安装与旧模式兼容；读取代码不等于启动业务或发送请求。小复现尚不证明整包已经修好，最终必须重做真实界面验收。版本选择和本决策等待开发者确认；确认前不启动正式修补任务，不替开发者登记对齐。
