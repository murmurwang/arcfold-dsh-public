# 决策：在测试账户会话中自动启动隔离验收并回报就绪状态

Status: proposed
observed_in_version: 0.5.1 隔离测试包；测试入口对应 main 1d5dac2
fixed_in: pending
user_verified: pending

## 来源

开发者反馈 F6（2026-11-16T11:09:04+00:00 登记）

## 问题

隔离验收已经使用专用普通账户、全新测试资料和本机合成模型，但每次仍要求开发者切到账户、在 Finder 找测试目录、双击启动文件、保留终端并回报窗口已打开。开发者希望把这些操作纳入本轮自动化。

已核对截图对应的 A16 和 0.5.1 测试包。当前 Start-Test.command 先核对账户和固定目录，再启动 Run-DSH.command，通过阶段标记和指定命令文件安排后续窗口。版本化入口 tools/dev-workflow/rehearsal/run.mjs 启动本机包下载与合成模型服务，desktop.mjs 的 requireTestAccount() 核对普通账户身份、操作系统和原版应用不可写；launch() 核对原版应用及测试资料，启动带独立资料目录的真实 DSH 窗口。当前 display() 已能核对测试进程并读取窗口内容，因此“窗口是否就绪”有程序核对基础。release.py 的 verify_isolated() 最终核对源码、安装包摘要和各项实测证据，启动窗口本身不算验收通过。

来源是本机反馈 F6；截图输入框中的文字不是已经执行的回报。本任务不代答 A16，也不接管正在进行的 0.5.1 验收。

## 方案

与审阅自动化在同一轮推进，但使用单独决策和任务，避免把密钥及费用执行与测试账户的系统权限混成同一项授权。

首次由开发者登录普通测试账户，在明确绑定安装内容和目标账户的授权下，配置只在该账户图形会话中运行的后台启动程序。macOS 为登录用户运行的后台程序称为 LaunchAgent；它随该账户会话可用而启动。[Apple 官方说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)

之后按下面的顺序运行：

1. 开发入口准备固定测试包和执行计划，记录旧版、新版、源码、两份产品包和测试脚本的内容摘要、目标账户及有效期；实际测试授权绑定这些对象。
2. 开发者在聊天批准后，Agent 登记原话，把该次测试加入队列。测试账户已登录且后台程序可用时自动领取；未登录时状态明确显示“等待登录测试账户”，不把请求已入队说成窗口已打开。
3. 测试账户程序重新核对自己的普通账户身份、原版应用签名、授权、脚本及包摘要，调用固定的版本化测试入口，自动启动本机模拟服务和测试 DSH；无需寻找 Finder 目录或保留终端。
4. 程序核对实际进程所属账户、测试资料目录、窗口内容读取入口与就绪页面，写回“窗口已就绪”或具体失败。主账户只读该回执，Agent 据此继续后续测试，不再要求开发者手写“窗口已打开”。
5. 后续安装、更新、失败恢复、重启和读回沿用真实测试过程及逐项证据。启动就绪、程序检查通过、实际验收通过分别记录。失败或未覆盖项不能变成 pass。

已登录但不在前台的测试会话能否稳定运行和读取真实窗口，需要实测；未经实测不承诺。若必须切到该会话才能操作界面，就只提示需要切换的具体阶段。电脑重启、测试账户退出登录或系统要求验证时，仍需开发者完成系统登录；不保存账户密码、不关闭系统保护，也不启用自动登录。

执行入口只接收固定动作和经过授权的测试包编号，不接受任意 shell 命令、任意可执行路径或来自待审提案的启动代码。主账户提交请求、测试账户写回结果的目录与权限分别固定，测试账户使用自己拥有的私人资料；本机共享文件仅是交接机制，不能被称为身份认证。

同一测试包只启动一次。已在运行时返回原任务；崩溃后先检查原进程、窗口和端口，不重复启动、不直接杀死不明进程。旧计划、过期计划、脚本变化、端口被占用或请求与回执不符时停止。支持暂停后续启动、取消未开始任务和按已批准计划卸载测试账户的后台程序。

先在独立工作目录完成实现与合成检查，再准备具体安装计划供核对。安装到测试账户、替换当前测试包及真实界面验收按绑定对象的授权执行。现有 A16 指向的测试材料保持原状，是否改用新入口由原验收任务按新材料重新核对。

## 预期效果

首次设置后，测试账户会话可用时，常规操作由“切换账户、找目录、双击、等待、手动回报”缩短为“批准测试、查看自动回报”；会话不可用时仅保留必要的系统登录或界面切换。审阅自动化与测试启动自动化分别保留授权、失败与实际验收证据。

## 考虑过的其他做法

直接从主账户用管理员权限启动应用：无法仅凭后台进程启动证明普通用户的真实图形会话和隔离条件，不作为默认方案。

关闭系统登录要求或保存测试账户密码：扩大凭据及系统安全变更，不在本任务范围内。

把整个验收改成无界面的模拟测试：可以补充程序检查，但不能替代现有真实原版 DSH 界面验收。

## 验收标准

- 测试会话已可用且授权有效时，只提交一次任务即可自动启动并取得真实就绪回执；不要求 Finder、终端或手写就绪回报。
- 会话未登录或无法访问真实窗口时，明确记录等待或 unconfirmed，不伪造就绪或验收通过。
- 重复提交、程序重启、窗口已存在、端口被占用时不产生重复实例，不误关其他程序。
- 错误账户、管理员账户、旧源码、包或脚本摘要变化、未批准及过期任务在启动前被拒绝。
- 使用合成包和模拟服务验证跨账户交接、队列、状态及恢复；真实跨账户 GUI 行为另行记录 pass、fail 或 unconfirmed。
- 日常用户资料、配置、凭据和实际 DSH 不被测试入口修改；真实模型发送次数为零。
- 卸载和暂停仅影响该测试启动程序，保留原测试资料和证据。

## 风险

系统登录、后台会话的图形能力、窗口读取权限和跨账户目录权限需要真实环境验证；现有脚本不能证明后台会话里全部界面动作已可用。本任务提供自动启动和如实回报，不保证绕过系统要求或让所有 UI 测试全天无人值守。

测试后台程序不持有审阅密钥，不与费用队列共用权限。两项任务可以在同一轮开发，但本决策需先展示并由开发者确认，再启动新的独立任务。
