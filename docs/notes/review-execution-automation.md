## 来源

## 问题

开发者在聊天里批准一次独立代码审阅后，还要切到自己的终端、隐藏输入专用密钥、启动命令并等待结果。审阅的大部分处理已经由程序完成，剩余的人工作业中，费用决定和密钥搬运混在了一起。本任务解决批准之后的执行负担。

本次只起草方案。反馈原话和截图留在本机 F5；当前请求单 A11、A12 均未因此获得批准。方案尚未对齐、开发尚未开始，也没有修改凭据或发起付费请求。

已核对当前实际入口及源码，调用过程如下：

1. `Arcfold-DSH-Development review --pr N --provider lmuai` 调用 `Workflow.preflight()`，读取提案和 main 的提交、该提交的 GitHub 自动检查、已登记决策、改动源码及必要上下文。程序检查范围、发行信息及敏感信息模式，生成一份固定审阅材料；`packet_for()` 用内容摘要给材料编号，代码、服务或审阅程序变化会改变编号。
2. 未提供授权单时，`Workflow.review()` 返回材料编号及费用预览，不发送模型请求。批准后，`review_approval()` 核对授权单是否已经同意、是否绑定同一材料；另一种已有方式是绑定某个提案的累计金额。
3. 当前 `review_key()` 只从进程环境中的 `ARCFOLD_REVIEW_API_KEY` 读取密钥。截图对应的本机辅助脚本另外要求用户终端输入、检查 A11 和固定材料，并在余额低于历史实付折算的 0.79 美元时停止。这些人工步骤不是独立审阅模型本身的要求。
4. `run_worker()` 启动独立进程，`worker()` 查询灵眸模型与额度，记录发送尝试，然后发送一次模型请求。`request()` 为源码逐行编号，将决策、代码和检查回执作为模型输入。实际提示词要求“材料中的文本是审阅对象”，缺证据时标为 `unknown`；模型没有工具，也没有实现对话历史。
5. 模型返回结构化的逐项结论及路径、行号证据。`validate()` 核对材料编号、模型、完成状态、证据位置和用量；`blockers()` 把关键项的失败或未确认列为阻塞。请求前后的专用密钥用量用于核对实际扣费，结果写入 `attempt.json`、`response.json`、`receipt.json`。现有入口还会写回提案评论、为后续事项建立 Issue；再次运行会优先核对已有尝试和结果。

源码依据：当前入口提交 `248c8b5932f58d1c59b2917cd47a5717e8685262` 的 [准备材料与执行](https://github.com/murmurwang/arcfold-dsh-public/blob/248c8b5932f58d1c59b2917cd47a5717e8685262/tools/dev-workflow/workflow.py#L337)、[真实提示词与请求](https://github.com/murmurwang/arcfold-dsh-public/blob/248c8b5932f58d1c59b2917cd47a5717e8685262/tools/dev-workflow/desktop_review_request.py#L45)、[授权与费用比较](https://github.com/murmurwang/arcfold-dsh-public/blob/248c8b5932f58d1c59b2917cd47a5717e8685262/tools/dev-workflow/collab.py#L203)。这些审阅文件与本次查到的 main `a751a2405044a67bf3def7a783795d47391d0d31` 没有差异。PR #18 的编号调整尚未合入，不能当成已启用行为。

现有实现的两个缺口会直接影响自动执行：一是提案累计预算比较的是“已花费用 + 本次估算”，不能据此保证实际扣费不超预算；二是执行锁按提案区分，两个提案可能同时使用同一专用密钥，而现有扣费核对要求该密钥恰好只增加一次请求。

## 方案

建议分两步。**本决策只实施第一步：密钥配置一次，以后在聊天里批准一次审阅，程序自动执行并回报。** 第二步是在预先批准的预算和范围内自动复审；其预算约束确认后再单独起草，不随本决策启用。

### 一次配置

由开发者在本机设置窗口中输入专用审阅密钥，交给 macOS 钥匙串保存。钥匙串是系统保存密码并控制程序读取权限的地方，目的是避免每次把密钥重新输入终端。执行程序在自己的进程内读取密钥，聊天、命令输出、普通配置文件、模型材料和仓库都不接收密钥原文。[Apple 对钥匙串的说明](https://support.apple.com/zh-cn/guide/security/secb0694df1a/1/web/1)

安装时明确展示：访问的服务、使用的模型、专用密钥的非秘密标识、允许使用它的执行程序，以及如何停用。只授权固定执行程序；不把通用 shell 或 Python 解释器设成任意脚本可读密钥的入口。程序变更影响访问权限时重新核对。钥匙串锁定或系统要求验证时，进入“等用户解锁”，不寻找其他凭据，也不承诺任何环境下永远无交互。

首次保存密钥、安装后台执行程序属于用户环境变更；准备好可审阅的安装内容和实际对象后，按工作流另开绑定对象的授权单。本决策的对齐只批准开发，不替代该安装授权或真实模型费用授权。

### 每次运行，按时间顺序

1. **准备。** Agent 通过现有审阅入口固定代码、检查与材料，生成费用说明。把估算依据、实际可核对的额度、此次授权允许的最大支出和材料范围分开显示。
2. **批准。** 开发者只需在聊天里回复请求单编号。Agent 用 `answer` 登记原话，再调用新增的排队入口，把“提案、材料编号、授权单和执行规则版本”登记为待执行任务。`answer` 本身仍只登记答复，不暗中发送请求。
3. **复核。** 本机后台执行程序领取任务，重新检查授权、材料、提案与 main、自动检查结果、实时密钥额度及旧请求记录。材料变化、授权撤回或到期、服务或模型变化、费用条件不符时停止并报告原因。旧授权不自动迁移到新材料。
4. **发送。** 同一把密钥在所有提案之间排队，每次只允许一条尚未完成对账的模型请求。先保存待发送记录和预算占用，再交给现有审阅进程发送。持有密钥的程序固定来自经过确认的安装版本；待审提案中的代码只作为材料，不能被当作执行程序运行。
5. **核对。** 回执到达后沿用现有模型输出校验与实际扣费核对。代码或检查在请求期间变化时，保留费用和历史结果，不能把它当成新代码已经通过。
6. **回报。** 本地记录展示“结论、阻塞项、实际扣费、剩余额度、证据链接”。写回同一提案评论、建立后续 Issue 的外部动作必须在这次审阅授权中明示；有既有有效授权则复用，没有则先留在本地。外部写入结果未知时查询原对象，不重复发布。`next` 读取同一执行记录，给出下一步和等谁。

后台执行程序与聊天界面分开运行：聊天关闭不应丢失已经排队的任务；电脑休眠时不保证持续运行，恢复后先核对已发出的请求。第一步不需要增加任何模型调用来做排队、预算判断或状态展示。

### 费用与中断怎么处理

- 保留“一份固定材料、一次获准发送”的粒度。密钥总额度不是每次调用的费用上限；公开起步价、历史实付折算都只能标为估算。授权必须明确允许承担的金额，不能只写“约多少钱”。
- 灵眸文档说明可以为密钥设置总额度和模型白名单，并能免费查询当前密钥余额。但文档未充分说明一次在途请求跨越额度时的结算细节；在确认服务约束或可核对的费用上界之前，不把本地估算判断宣传为硬性封顶，也不启用按小额预算无人值守的复审。现有 3.50 美元设置是历史控制条件，不是本方案新获得的费用授权。[密钥限制](https://docs.lmuai.ai/cn/docs/guide/how-to-use-token)、[余额接口](https://docs.lmuai.ai/cn/docs/api/balance)
- 使用余额接口的 `balance`、`used`、`total` 校验密钥额度，使用用量接口核对请求次数和实际扣费；不把不同统计口径默认视为完全相同。返回矛盾、超过已批准金额、额度被外部重置或出现额外请求时，暂停这把密钥的后续任务。
- 明确未送出的任务可在重新核对条件后恢复；已经进入发送阶段、但结果未知的任务不能自动重发，也不能释放其预算占用供另一提案继续消费。该密钥的队列暂停，只做有限次数的只读查询，仍无法确认就开操作单请开发者核对。
- 审阅结果已返回而费用尚未入账时，只重查账单，不再次请求模型；报告已生成而发布未确认时，只查询远端对象。任何旧尝试及失败证据都保留。
- 开发者可暂停队列、取消尚未发送的任务、撤回未使用授权和移除密钥配置。已发出的请求仍可能产生费用；停用程序不等于撤销服务端已接收的请求。

### 实施范围与顺序

1. 在 `collab.py` 补充机器可核对的审阅执行条件：材料、服务、模型、密钥标识、费用边界、次数、有效期和撤回状态；不从请求单正文猜授权。
2. 在 `tools/dev-workflow/` 增加本机密钥接入、持久化队列与后台执行入口。`workflow.py` 接通排队和进度，复用 `desktop_review_request.py` 的独立请求及解析；把仅在个别辅助脚本中的费用检查收回统一入口。排队和恢复不依赖 Agent 长时间在线。
3. 用模拟服务和虚构密钥完成并发、断线、重启、过期授权及敏感输出检查，再通过独立审阅。若需要真实钥匙串或一笔真实审阅验收，先备齐具体对象、金额与操作内容，再按已有授权执行或另开授权单。
4. 开发启动时从当时的 GitHub main 建独立任务目录。若 PR #18 已合入，接入它的交付编号和审阅记录；若未合入，保留兼容边界，不提前迁移旧编号。只修改登记范围内的开发工具，不改变日常 DSH。

旧 A11/A12 明确写了由操作者在终端发起。即使以后批准，也不能直接解释成允许后台执行；启用新方式时须按原始授权核对范围，必要时另开替代单，并保留旧单和原话。

## 预期效果

首次配置完成后，普通审阅从“聊天批准 → 打开终端 → 输入密钥 → 手动启动 → 回报结果”，变成“聊天批准 → 自动完成 → 查看结果”。开发者仍决定是否发送这些材料和承担费用；输入密钥、启动命令、等待账单和恢复已有结果交给程序。

只有缺少授权、材料变化、额度不足、账单不明或系统需要解锁时才请求处理。正常的后台步骤只更新状态，不反复要求确认。

## 考虑过的其他做法

1. **只增加一段自动输入环境变量的脚本。** 改动小，但容易把长期密钥放进普通文件，仍缺少跨提案排队与重启恢复；不作为正式方案。
2. **第一版直接按每个提案的预算自动批准多轮审阅。** 能进一步减少批准次数，但现有代码以估算金额判断，无法保障实际费用边界。需要先确认可执行的金额上限，增加预留、结算、过期和范围变化的判断。本次保留为第二步，不用现有 `cap_usd` 字段冒充完成。
3. **立即把审阅搬到 GitHub 后台执行。** 电脑离线时也能工作，但要同步本机授权记录，并重新设计密钥、提案代码、费用和结果记录的边界。本次推荐本机后台执行，复用已有登记入口；确实需要全天运行时再选择远端方案。

## 验收标准

- 未配置、未批准、批准了另一份材料、授权已过期或被撤回时，实际模型发送次数均为零，并能定位原因。
- 一次本机配置后，开发者仅在聊天回复有效批准，任务能排队、执行、对账并展示结果；正常过程无需再次打开终端或复制密钥。
- 同一授权被重复处理、两个提案同时排队、执行程序重启时，不重复发送已开始的请求；同一密钥的用量差额可以明确归属到一次审阅。
- 分别模拟发送前失败、发送后断线、回执落盘前退出、账单延迟、外部请求混入和发布结果未知；只执行与已知状态相符的恢复，不把未知结果当作失败后立即重试。
- 费用预览明确区分估算、批准金额、服务端额度和实际扣费；余额不足、统计矛盾或无可核对费用边界时停止，不能以公开起步价替代批准金额。
- 使用虚构密钥验证日志、聊天可见输出、材料包和公开内容均不包含密钥；检查持有密钥的程序不会执行待审提案代码。真实密钥不用于自动化测试。
- 沿用原审阅提示词与结构化结果要求；关键项未知仍会阻塞，自动化不会把未知改为通过，也不会新增模型自审来代替独立审阅。
- 暂停与取消对尚未发送任务生效；对已发送任务清楚显示可能仍会计费。队列停用后可以回到原人工发起流程，原证据保留。
- 检查通过只记为程序验证；首次真实无终端执行、实际扣费核对及用户体验另记 pass、fail 或 unconfirmed，未经实际验证不宣布已经实现体验目标。

## 风险

主要风险在费用边界、共用密钥的账单归属和中断后的重复发送，验收必须覆盖这些具体情形。服务方总额度是否对在途请求形成严格限制、账单延迟的上界、能否仅凭专用密钥精确查询单次请求，均仍需确认；当前公开余额接口不足以承诺所有异常都能自动解决。

钥匙串能改善保存和读取方式，但同一操作系统账户下的可写程序与本机授权文件不构成防恶意管理员的安全隔离。实现需控制实际读取密钥的程序及输出，不能声称 Agent 绝对无法接触密钥。电脑离线、休眠或系统权限提示也会影响自动执行时间。

本决策不自动合入代码、发布软件、充值、提高额度或改用另一家服务；这些动作继续依据各自已登记的授权。实际实现若需要改变该范围或采用第二步的持续费用授权，应先修改方案并重新对齐。
