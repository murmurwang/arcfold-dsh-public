# 决策：[072-D2] 升级后的原会话选模保存后同步页面

Status: proposed
observed_in_version: 0.8.0
fixed_in: pending
user_verified: pending

## 来源

交付 068 的 0.8.0 第一次候选。最新普通账户真实窗口验收中，原生菜单选择 GPT 后，会话日志第 25 条已保存 GPT，服务端同一会话的当前状态也返回 GPT；页面使用的模型状态及按钮仍是 DeepSeek。工具基准、旧对话、失败下载恢复、更新、原生设置确认、全新安装和工具核对通过；升级后第二条消息、配置刷新及重启读回尚未执行。全部使用本机模拟模型，真实模型请求为零。

## 问题

问题已缩小为：已保存的新选择没有进入页面共享的会话状态。还不能断言是更新时持续推送中断，还是页面没有接受某次推送。先前关于保存顺序的假设没有成立，原登记的后台保存处理也不在真实 Desktop 调用链中；本任务不修改那条处理链。

## 方案

在原任务、原分支继续修复。仅在 Arcfold 会话的界面适配中，观察原生选模操作从保存中变为成功；随后只读一次该会话的服务端当前状态。把服务端返回的完整、带顺序编号的状态交给 DSH 已有的页面接收入口，让原生模型按钮和共享会话状态从真实记录更新。这里的状态是程序从会话记录生成、供页面显示的结果，不是 Agent 推断的选择。

使用 DSH 现有的模型目录可观察状态、`remote.session.projections` 读取入口及 `sessions.handleControlFrame` 接收入口；沿用原生“较新的记录优先”的规则，不直接改模型按钮、不改宿主应用文件、不手工拼造已保存结果。正常推送先到时，补读不覆盖它之后的新选择。

只在一次明确成功的选模后补读一次，不轮询，不重放选择，不刷新整个页面或重新连接。失败、取消、连接已换代、界面卸载或后续选择已开始时，丢弃旧结果。补读失败保留实际状态与诊断，不能据此宣称选择已读回。原生回答中限制、可用性检查、默认模型保存及权限规则不变。

改动范围改为：`packages/method-ui/src/tree-client.mjs`、新增 `packages/method-ui/src/native-model-readback.mjs`、新增 `test/native-model-readback-ui.test.mjs`、新增 `docs/native-model-readback.md`、原任务决策说明及更新说明。若现有可观察状态无法可靠区分保存成功，或真实修复仍需别的范围，先停下修订，不能替换原生选模方法来绕过。

本任务仍不改版本、不安装日常组件、不发布。合入后另行对齐新的 0.8.0 发行范围；主线在原候选之后新增的功能不得自动带入。继续本机模拟及既有暂停付费审阅规则，预计新增费用 0 美元，真实模型请求为零。

## 预期效果

用户升级后回到原会话，在原生菜单选模型及推理等级，页面、已保存记录和下一条请求一致；旧对话和目标保留，刷新和重启后仍能读回同一选择。

## 考虑过的其他做法

- 调整后台保存顺序：真实 Desktop 没有使用原登记的后台处理，而且本次已证明新选择保存成功，不能在无关链路上修。
- 只按点击值立即改页面：会掩盖保存失败，不采用。
- 重启整个连接或页面：影响范围更大；本方案只补读已完成操作的原生状态。
- 忽略升级失败继续发布：没有豁免，继续保留阻塞。

## 验收标准

- 有针对性的本机测试覆盖：成功后仅补读一次，失败不补读，真实推送先到及后续新选择优先，连接换代和卸载后的迟到结果丢弃，读取失败不伪造成功，使用真实服务端顺序编号。
- 以原生页面状态接收模块验证回写规则，不能只用一个会无条件接受结果的假对象证明通过。
- 修复进入经另行确认的新候选后，普通账户真实窗口通过原生菜单切换升级前原会话的模型和推理等级；页面、持久记录、实际请求头和本机模拟服务一致，刷新及重启仍一致。
- 标准工具基准与 Arcfold 工具清单继续一致，完整隔离验收通过。旧候选各次失败及三项功能未确认均保留，不自动变成新候选通过。

## 风险

尚未定位持续推送没有更新页面的更底层原因；这里补上成功操作后的权威读回，不能宣称已修好宿主所有推送。页面生命周期与并发选择可能让旧读回晚到，必须按连接代次、操作次序和宿主记录编号共同防止回退。修复尚未实施，以上效果均待验证。
