# 决策：[063-D2] 每轮替换上一轮编号表，主对话缓存从上一轮断开

Status: proposed
observed_in_version: 0.7.0 + main@8b432a6（测试版）
fixed_in: pending
user_verified: pending

## 来源

Agent 查看测试版目标树记录和一段主对话的会话记录时发现。数据是测试版 2026-11-19 至 11-20 的预览备份。Murphy 原话：draft 2345

## 问题

<!-- 谁在什么场景遇到什么，实际发生了什么，证据在哪里。一份决策只写一个问题。 -->
每轮主对话开始时，Arcfold 往对话里加一段编号表（turn-authority）：本轮的当前目标、从根到它的路径、各节点的版本号和本轮的证据编号（`src/tree/runtime.mjs:76`）。这段的 key 带着本轮编号（`runtime.mjs:83`，`turn-authority:<轮编号>`）。

下一轮开始时，新背景里没有上一轮的 key，上一轮那段就被原地替换成一行 `[previous Arcfold component retired]`（`src/tree/context.mjs:190`，替换上一轮那条消息的位置）。改动发生在上一轮中间，服务商的前缀缓存从这里断开：这一轮第一步，上一轮整轮的助手回答和工具结果都要按没缓存的价格重算一次。

别的背景段（全局概貌、各节点）已经按"同一 key 保留旧版、追加新版"的办法保持前缀不变（`context.mjs:185` 的注释写的就是为了前缀稳定），只有编号表每轮换 key。

### 实际例子

预览备份里一段 41 轮的主对话，会话记录里每一轮开始都有一次替换上一轮编号表的操作：第 2 轮替换了第 1 轮那条（事件 106 替换 12），第 3 轮替换第 2 轮那条（185 替换 112），一直到最后一轮。

这样每轮的内容至少要按没缓存的价格多算一遍，一个会话合计大约多算一遍整段对话的长度。这段对话最后一次请求的输入是 23.0 万 token。

这段对话实际没命中缓存的比这多得多：大多数轮的第一步只命中 6,528 token，同一轮内部、编号表没动的时候也常整段没命中。那部分原因不在 Arcfold 代码里，本决策不处理。

## 方案

1. 编号表的 key 改成按本轮当前目标算：`turn-authority:<当前目标编号排序后的摘要>`，不带轮编号。当前目标和上一轮一样时，按现有的保留规则，上一轮那段留在原位不动，本轮新的一份追加在本轮用户话后面。当前目标变了（换了目标、多了或少了目标），key 不同，上一轮那段照旧原地撤掉。
2. 编号表的说明补一句："以最后一份编号表为准，之前编号表里的版本号和证据编号已经失效。"
3. 工具照旧核对版本号。模型如果抄了旧编号表里的版本号，会得到 REVISION_CONFLICT，树不变，不会改错。

不改的部分：跨聊天经历段换版时照旧原地撤掉（里面可能有其他分支的内容，范围变了必须撤）；全局概貌和节点背景的规则不变。

## 预期效果

- 连续在同一组目标上聊时，新一轮开始不再改动上一轮的历史，前缀缓存能一直延续到上一轮末尾。换目标的那一轮照旧会断开一次。
- 按上面那段 41 轮的对话估算，一个会话少按没缓存的价格算大约一遍整段对话（约 20 万 token 量级）。实际能省多少，取决于服务商缓存本身命中得怎么样。

## 考虑过的其他做法

<!-- 只写真实考虑过的做法和放弃的原因。 -->
- 编号表不进历史，只在每次请求的末尾临时附上：前缀最稳，但现在发送前要核对实际消息和已挂载的背景完全一致，曝光记录也按消息记，这些都要改，改动大。
- 保留替换，但把编号表挪到历史更前面：替换的位置更靠前，缓存断得更早，更糟。
- 不处理：每轮都多付上一轮的钱，会话越长越多。
- key 改成固定的 `turn-authority`（D1 的写法）：开发时发现这样换了目标以后，旧编号表也一直留着，里面有旧目标的名字和路径。用户为本聊天选了某个分支时，全局概貌只列分支里的目标，旧编号表却会把分支外的目标名留在对话里；现在换目标时是撤掉的。按当前目标算 key，换目标时的行为跟现在一样，只在目标没变时保留。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

- 测试：连续两轮，第二轮开始后第一轮的编号表原样保留，会话记录里没有替换操作；第二轮的新编号表追加在第二轮用户话后面；发送前核对通过。
- 测试：模型用第一轮编号表里的版本号调 arcfold_revise_goal，报 REVISION_CONFLICT，树不变；用最后一份的版本号照旧成功。
- 测试：第三轮换到另一个目标，上一轮的编号表照旧原地撤掉，这一轮只看到新的一份。
- 测试：跨聊天经历段换版时照旧原地撤掉；全局概貌、节点背景的保留和追加不变。
- 原生测试：两轮对话，第二轮第一步发出的消息，前面部分和第一轮最后一步发出的消息逐条相同。

## 风险

- 历史里会留着好几份编号表，模型可能抄错旧的版本号或证据编号，工具报冲突后要再调一次。
- 每份编号表约 450 字，以前撤掉后只剩一行，现在同一组目标上的整份留着。41 轮都在同一目标上的会话会多出约 1.8 万字，直到对话被压缩。
- 实际省多少受服务商缓存命中率限制。按现在的数据，主对话缓存本来就不稳，省下的可能比估算少。
