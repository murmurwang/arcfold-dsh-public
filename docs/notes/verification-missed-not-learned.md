# 决策：[065-D2] 检验找出的漏记只记成错误，没补进理解

Status: proposed
observed_in_version: 0.7.0；源码基线 2ee8850
fixed_in: pending
user_verified: pending

## 来源

公开源码中可以复核的行为，基线为 2ee8850。

## 问题

检验报告能够指出上一轮学习漏掉了什么，但程序只增加一条修复记录。后续在相同目标上开始新的对话时，主助手仍读不到已经找出的理解。

## 方案

只改检验写入 missed 的地方。

1. 每条 missed 照旧写修复记录，用于统计学习出错，不变。
2. 同时把它写成一条理解：内容取 missed 的 what，来源编号取它的 evidence。证据里有用户原话时，来源记为用户明说，否则记为助手推断；验证状态都是未验证。写入沿用 proposals 新增理解的同一条路径（commitProposal），来历记为 missed。
3. 挂在哪个节点：取证据所在轮次归属的节点，与本次检验覆盖的节点求交集；交集为空时挂到本次检验的节点。
4. 目标节点上已有内容完全相同的有效理解时，不重复写入。
5. 写入失败时（内容超长、来源无法解析等），只保留修复记录，并记一条带检验任务号的诊断，不让整次检验作废。

## 预期效果

- 检验发现的漏记会作为未验证的理解进入对应目标。下次在这个目标工作时，主助手能读到理解内容。
- 修复记录和学习出错的统计不变。
- 不增加模型调用，费用不变。

## 考虑过的其他做法

- 改提示，让检验把漏记放进 proposals：proposals 现在对日常提案限一条，漏记经常一次好几条，放宽限制会让一般提案也变多，不采用。
- 漏记只放进下一轮背景、不存成条目：下一次离开节点就丢了，也不能被后续检验支持或推翻，不采用。

## 验收标准

- 模型拿到的工具和原版 DSH 一致：未安装 Arcfold 时用 standard 取原版完整工具基准；安装后 arcfold-main 核对 bash、read、write、edit、glob、grep（Arcfold 会关闭 standard）。实际会话 request/header 与模拟服务收到的清单均须核对，缺项判失败。

- 测试：检验输出含一条 missed，证据是用户原话：写入一条有效理解，来源为用户明说、未验证，来源编号等于 evidence，修复记录照旧存在。
- 测试：证据只有助手回答的 missed，理解的来源记为助手推断。
- 测试：证据轮次归属节点在检验覆盖范围内时挂在该节点；不在范围内时挂在检验节点。
- 测试：同一节点已有内容相同的有效理解时不再写入；修复记录仍写。
- 测试：missed 内容超过理解长度上限时不写理解，修复记录写入，留下带检验任务号的诊断，同批其他操作照常生效。
- 测试：写入后的下一轮主助手输入里，对应节点背景包含这条理解。

## 风险

- 漏记的表述是检验模型事后的概括，可能不准。写成未验证的理解，之后的检验可以支持、改写或作废它；用户也能在界面撤回。
- 检验对同一件事每次都报 missed，会累积措辞不同的近似条目。完全相同才去重，近似重复交给后续检验的 merge 处理，这里不做语义去重。
