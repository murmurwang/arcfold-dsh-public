# 完全重启时的运行代码加载修补

0.5.1 在原版 DSH 0.2.2-rc.1 的隔离账户验收中，安装与更新成功，但完全退出重开后 Arcfold 核心组件加载失败，会话服务不可用。插件刷新暂时恢复；再次完全重启仍可复现。这个候选没有完成发行验收。

## 已定位的过程

1. DSH 读取 Arcfold 入口，等待会话与模型服务就绪。旧入口此时尚未导入树运行代码。
2. 服务就绪后，入口在 `apply()` 中动态导入 `src/tree/runtime.mjs`。它会加载 `deepseek-transport.mjs`、`metered-transport.mjs` 和 `undici`。
3. 同时，DSH 的配置观察器在应用就绪后进行首次刷新。其 `Hmr.reconcileProfile()` 清理没有可读导出对象的模块；尚在加载的模块也符合这一条件。
4. 隔离诊断直接记录到 `Hmr.evict()` 删除尚未执行完的 `undici/index.js` 加载记录。Node 随后进入 `loadCJSModuleWithModuleLoad()`，发现记录不一致，报 `ERR_INTERNAL_ASSERTION`。

诊断使用的原应用归档摘要为 `f21d83abfb33d463822a52c439cc9b15c8245dbce4ae4cf9424c90eae8eba94f`，Electron 44.7.0、Node 24.21.0。诊断插件和额外启动日志开关只用于隔离账户，已经移除；不写入产品。

## 改动

`src/index.mjs` 在模块读取时静态导入运行代码，先完成依赖连接，再进入核心组件启动。运行代码只导入一次；不捕获并重试失败的模型请求，也不改变 DSH 自身的刷新机制。

运行代码的导入与业务启动仍是两个步骤。`apply()` 继续检查设置和原生确认记录，通过后才调用 `installTreeRuntime()`。未确认的新资料不能启动树流程；旧模式仍要求明确的数据位置。

## 检查与范围

`test/desktop-cold-start.test.mjs` 每次启动独立子进程，使用真实 DSH Loader、配置观察器和 HMR，在已观测的时序下释放应用就绪信号。冻结的 0.5.1 入口作为失败对照，当前真实入口作为修补组。检查实际发生的依赖清理、组件结果、确认规则及旧模式数据要求，外发网络被拒绝。

对照入口触发同一断言错误，修补入口可以进入运行配置校验，且没有过早清除依赖。相同检查也在上述原签名应用自带的运行环境中通过。此回归仅验证加载与入口边界：故意不提供运行资料位置，因此不启动实际数据库、后台任务或模型请求。完整产品检查、独立审阅和最终整包的隔离界面验收仍分别记录；本说明不替代最终发行回执。

0.5.2 接续原生模型配置与许可材料。0.5.1 已有标签和草稿，保留原包、审阅与失败证据，不替换成修补包。
