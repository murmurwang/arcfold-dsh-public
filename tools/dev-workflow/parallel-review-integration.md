# 并行开发与统一审阅入口的衔接

多项提案可以同时开发和检查，但同一仓库只有准备最先合入的一项能进入付费审阅。负责发送请求的入口判断这一条件；进度页和构建工具读取它的结果，不自行计算另一份合入顺序。

本说明落实已确认的队首审阅修订，以及开发者随后指定的实现归属。统一审阅交付负责队首判定和发送限制；并行开发交付负责步骤、候选构建、组合验证和启用衔接。

## 已核对的实现与接入位置

- 并行开发兼容批次的 `Workflow.merge` 在独立审阅通过后调用 `merge_queue.enqueue`，再于实际主线写入前调用 `merge_queue.require_turn`。这是合入准备的旧安排，不能直接充当发送前的队首判定。
- 原审阅自动化实现的 `review_queue.enqueue/process` 管理已批准材料、实际发送和核账。统一审阅交付正在调整此入口；接入必须以它最终提供的明确提交和实际调用接口为准，不能把旧草案当作正式接口。
- `execution.view` 与 `collab.progress` 提供并行步骤和总览；`ci_evidence` 读取同一提交的实际检查证据。它们保留自己的职责，不据此批准或发送审阅。
- `parallel_build` 与 `release_candidates` 管理固定候选的构建与发布条件，不持有付费审阅顺序，也不保存审阅密钥。

## 实现归属

| 行为 | 负责实现 | 并行开发的接入方式 |
|---|---|---|
| 决定付费审阅队首，维护顺序和占用 | 统一审阅入口 | 读取该入口的实际结果；不另建队首选择函数或另一份顺序表 |
| 发送前检查授权、预算、密钥及未结清请求 | 统一审阅入口 | 调用统一入口，不另发模型请求、不读取或保存密钥 |
| 展示目前轮到谁、等待谁及原因 | 并行开发的总览 | 展示来源结果及其检查对象；不能根据旧费用批准推导“现在可发送” |
| 独立源码、检查、材料准备和候选构建 | 各自已登记任务 | 只等待实际消费的前置结果，不因等待审阅轮次停止整项工作 |
| 实际合入及远端结果核对 | 原受管合入入口 | 消费统一顺序判定，继续核对当前提交、基线、检查和独立审阅 |
| 启用兼容读取及拆分检查布局 | 并行开发交付 | 先验证并部署兼容读取，再启用新布局 |

## 接入时的实际顺序

1. 各任务保存固定源码、自己的检查和材料。非队首仍能完成这些工作。
2. 统一审阅入口判断当前允许发送的提案。总览只展示这一判断，不能用创建时间、检查完成时间或现有审阅报告重新排一次顺序。
3. 只有统一入口在发送前确认条件仍满足，才执行付费请求。此前读取的进度快照不充当发送许可。
4. 原受管合入入口在真实主线写入之前消费同一份顺序约束，并核对其针对的仓库、提案和源码。模型运行期间不长期持有主线写锁。
5. 原请求、费用及合入结果查清后，由统一入口更新顺序；并行总览重新读取。异常和迟到结果保留在原尝试中，不被另一个任务覆盖。

统一入口尚未提供结果、结果不可用或对应对象已变化时，总览显示具体依赖尚未就绪，不能推断为可以付费审阅。无关的本地工作继续。

## 组合验收

接入以两侧固定提交建立临时组合，并保存所用接口、检查日志和结果。所选接口的名称、返回格式和错误路径必须从统一审阅入口实际代码取得，本说明不预设另一套尚不存在的调用协议。

组合检查应证明：非队首的人工与后台路径均不发送；总览与发送入口引用同一判断；主线前进后重新核对实际组合；重复读取进度不产生请求或状态写入；失效结果不会被当作许可；等待审阅轮次时独立检查和候选构建仍可继续。

这些本地检查不能替代最终主线组合的自动检查、适用独立审阅或正式启用记录。旧第一批代码、批准和失败证据保留，新的发送条件不能沿用与当前材料不匹配的旧授权。
