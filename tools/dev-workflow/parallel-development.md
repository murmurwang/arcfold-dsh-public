# 按实际依赖并行开发

一个任务等前置合入时，另一个任务可以继续编码；同一任务里不使用该前置结果的步骤也可以继续。每项任务仍从启动时的 GitHub main 建独立目录。方案范围、对齐、正式检查、独立审阅、合入和用户验收的要求不变。

需要等待的是具体结果或正在被修改的对象。例如，组合检查需要另一项功能的固定提交，同一测试实例需要上一轮更新结束，同一计费密钥需要上一条请求完成对账。文件范围重叠只提示组合风险，不自动阻塞整个任务。

## 登记与领取步骤

步骤计划是本机工程记录，不替代已确认决策，也不另发面向开发者的交付编号。先以现有流程完成 `new`、`check`、`align`、`start`，再运行：

```sh
./Arcfold-DSH-Development execution-plan feature-two --input steps.json
./Arcfold-DSH-Development execution-status
./Arcfold-DSH-Development next
```

`steps.json` 示例；两个任务须已经登记，前置步骤可以稍后登记：

```json
{
  "steps": [
    {
      "id": "local-work",
      "title": "完成不依赖前置功能的实现",
      "inputs": {"contract": "已确认的输入输出说明"},
      "output": "实现提交和检查记录",
      "resources": ["checkout:feature-two"]
    },
    {
      "id": "integration",
      "title": "检查两项功能如何组合",
      "inputs": {"contract": "已确认的组合行为"},
      "needs": [{"step": "feature-one/source", "reason": "需要第一项功能实际提交的接口实现"}],
      "output": "固定两侧提交的组合检查证据"
    },
    {
      "id": "workflow-checks",
      "title": "检查当前固定源码的工作流",
      "recipe": "workflow-checks",
      "output": "独立源码副本的检查日志"
    }
  ]
}
```

`needs` 指明实际结果与原因，登记时拒绝循环。任务名称经现有 `flow.task` 解析，不分配第二套任务号。`inputs` 的内容、依赖步骤的实际完成记录、决策或配方输入发生变化时，只让受影响的步骤重新就绪。其他步骤已有证据继续保留。

Agent 负责编码步骤。先 `execution-claim feature-two --step local-work`，保存返回的执行编号；完成后用 `execution-finish --run 编号 --outcome pass|fail|unknown --evidence FILE` 登记实际证据。证据另存一份并校验内容。`external: true` 仅表明步骤涉及外部后果，不授予发送、合入或发布权限；真实动作仍由对应受管入口执行。

同一组输入重复领取返回同一执行。输入变化后，旧执行仍保留；迟到结果只能写回原执行。旧执行占用的对象在结果核清前不释放。任务结束、进程退出或超过预期时长均不是重发依据。

共享对象使用稳定名称，如 `checkout:feature-two`、`test-profile:isolated-one`。同一对象的执行互斥，不同对象继续推进。对主线、候选和审阅密钥的真实保护仍在其各自入口，不能靠任意填写一个步骤名称绕过。

## 自动检查、资源与恢复

`execution-run [--task ID]` 运行已经就绪的离线检查，完成后重新判断后续步骤。它只接受 `workflow-checks` 和 `desktop-checks` 两种配方，不执行计划中的任意命令，不调用模型。默认同一状态目录最多两个重计算工作；用 `execution-limit --jobs 1` 可降为串行。正式构建也占用同一个额度，额度不足两个时两次构建顺序进行。

自动检查只接受干净、已提交的源码，另建独立副本执行。Desktop 配方的 `inputs` 还需要 `dependencies`（冻结依赖安装目录）和 `python_archive`（随包 Python 归档路径）。记录绑定源码树、Node/Python 与执行器版本、依赖锁及实际依赖文件内容、归档内容。运行前创建依赖副本并重新核对，测试子进程并发数为一，避免两个外层执行各自无限展开。Python 归档由固定源码中的校验函数验证后，解到本次运行目录。

普通状态事务只在读改写执行记录时持锁，文件内容检查在锁外完成；执行记录变化时重新领取，不在记录锁内等待下载、测试或模型。源码目录、可写依赖、临时目录和输出互相隔离。协调边界是共用这一套本机状态的入口，不是跨机器锁。

本地检查超时会停止其进程组并保留失败日志。进程突然消失时仍显示运行或未知；先确认原进程和其子进程已经退出、原对象的真实结果，再用 `execution-finish` 附核对证据。外部写入必须查询原服务的请求或对象，不能把超时写成失败并重新发送。`execution-retry --run 编号 --evidence FILE` 只接受已经确认失败的本地步骤；旧失败保留，新执行使用新编号。未知记录无法走这个重试入口。

`execution-metrics` 只读显示实际运行区间、重叠额度、重复执行次数和执行器观察到的等待原因。等待时间来自执行器观察间隔，不是连续监控；“从登记到开始”也包含 Agent 尚未领取的时间，不能全部算作机器等待。模型实际费用仍读取已有审阅及对账记录。

可用同一批合成工作比较串行与并行：

```sh
python3 -B tools/dev-workflow/rehearsal/parallel_benchmark.py --output /tmp/parallel-benchmark.json
```

该演练使用真实领取、独立进程和结果记录，但工作负载是合成等待。它验证机制和测量方法，不证明真实开发或产品体验已经提速。

## 提前提交，保留最终组合验证

`submit` 允许从仍属于主线历史的旧起点上传草稿，登记真实起点及 `needs_rebase`。`review-materials --pr N` 在 `previews` 保存固定材料，不需要先等待自动检查，也不发送模型请求。预览不能充当正式审阅、费用授权或合入证据。

付费终审前再组合最新主线，运行检查并生成正式材料。`review`、`verify_receipt` 和 `merge` 仍核对同一主线起点、源码、检查及审阅；文件不重叠不能沿用旧组合的放行。

明确调用 `merge` 且审阅通过后才登记合入排队。核对材料和退出草稿不占主线锁；实际主线写入及结果核对互斥。就绪候选中先处理等待较久者，基线过期或有未答决定单的候选只等待自己的条件。`merge-queue` 只读显示队列，`merge-unqueue --pr N --reason 说明` 保留退出原因；退出排队不解除未知远端写入的占用。队列不会自行批准或批量合入。

## 源码交付与发行组装

插件任务在确认前的决策头部明确写：

```text
fixed_in: pending
release_mode: source
release_note: 本次功能的实际改动说明
```

这允许功能先合入，保持两份包及锁文件的共享版本不变。实际依赖或功能源码可以按登记范围修改。进度显示“源码已合入、待发行”，不会当作纯 dev 改动关闭。每份源码回执保存任务、提交和独立审阅来源。

准备发行时，用单独的组装任务统一两份包版本、锁文件和更新说明：

```text
fixed_in: 0.6.0
release_mode: assembly
release_base: 前一份受管发行的完整源码提交
release_includes: feature-one,feature-two
```

`release-plan ID --base SHA` 提供实际源码所含的来源清单。工具逐一核对起点到组装基线的所有合入、实际文件树、父提交及审阅回执，既包含插件任务，也保留区间中的 dev 改动。未知合入、遗漏的来源、清单不符均拒绝。组装只能修改四份共享发行文件与本项决策，仍需自己完成检查、独立审阅和受管合入。

启动组装时短暂保留目标版本，另一活动组装不能争用同一版本；退出的旧任务和记录保留。旧流程中已经登记的版本仍按原回执识别，不能将现存版本改写成新归属。待发行任务的体验反馈可通过真实包含它的组装发行闭环，验收结论仍来自实际观察。

## 构建与分阶段启用

`parallel_build.prepare` 对受管合入的固定源码运行两次独立构建；分别安装依赖、构建与核对 npm dry-run，逐字节比较两组包。只有经固定源码校验的下载归档共享，两个可写依赖目录、安装缓存和输出不同。两份构建清单与失败尝试保留。构建不持有主线锁，主线前进不使这个固定源码的构建证据消失。

保留候选的正式发行依赖 A9 的 `release_candidates` 记录；本模块通过它的 `current` 检查候选，绝不另建候选索引。当前兼容批次保留旧发行入口的主线位置要求，不能提前从任意旧提交发布。接入候选入口时必须一起完成：

1. 构建前短暂选择候选，释放候选锁后调用 `parallel_build.prepare`；完成后再取同一版本锁核对。不能在外层持有 `candidate` 锁再调用构建助手。
2. 候选构建配方纳入 `parallel_build.py` 与 `execution.py` 的内容身份；输入变化产生新候选。复建和对外发布改查所选来源仍在主线历史，而非等于最新主线。
3. 普通 `source` 合入只记待发行；`assembly` 及已明确引用旧候选的修补才交给 A9 登记候选。组装来源任务、决策要求和审阅要求须加入同一次候选，不能只保留组装任务的要求。
4. 同版本对外写入持续占用候选，部分成功只恢复相同包；npm 默认更新指向按同一包组协调。A9 的实际验收、授权及结果未知保护继续生效。

审阅自动发送和同一计费密钥从发送到对账完成的独占由 A13 负责；这里不安装第二个执行程序或保存密钥。A9、A13 和编号实现都须按其实际提交做组合检查，不能把它们尚未合入的代码当作已上线。

自动检查也分两次启用：本批先提供 `ci_evidence`，接受真实旧作业与新的三作业回执。`desktop-checks-parallel.yml` 是未激活模板，放在工作流工具目录，不改变当前 GitHub 作业。兼容入口合入并实际切换后，再以受管改动替换 `.github/workflows/desktop-checks.yml`。两项检查取得同一提交，最后仍叫 `Desktop checks` 的作业要求两项都成功；缺失、取消、跳过或失败均拒绝。正式审阅读取两项真实日志和提交，不能只信汇总名称。

切换入口和启用新记录前先核清正在进行的写入，保留旧入口与状态副本。回退可以继续读旧记录和开发独立源码，不能让旧程序写入它不理解的来源、候选或执行记录。本批不自动切换正式入口、不修改日常安装，不激活模板，也不登记虚构的用户验收。
