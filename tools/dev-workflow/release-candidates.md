# 未发布版本的候选与修补

发布前发现安装或随包材料有问题时，先保存这次源码、安装包和失败记录，再修补并重新验证。同一目标版本下，每一份准备交付的源码及其构建输入称为一次候选。入口保存完整标识供程序核对，进度中显示“第几次候选”，不另设人工材料编号。核心包与界面包始终成组处理。

## 准备与查看

受管合入发行改动时建立候选。普通 `release --version X` 和加 `--prepare` 都只构建本机包；源码仍须是当前 main，并有对应的自动检查和独立审阅。每次构建两遍，逐字节比较包，保存依赖、许可及 npm dry-run 结果。

```sh
./Arcfold-DSH-Development release --version X --prepare
./Arcfold-DSH-Development candidate --version X
```

查看命令只读本机文件，返回当前候选、前后关系、每次原包目录、待办及发布记录。它不会把远端状态自动视作最新；提交审阅、合入和最终发布时会另行查询。

原包位于 `releases/X/candidates/<完整标识>/`；`candidate.json` 固定源码、合入、审阅和构建入口内容。`release.json` 绑定两份包校验值与两次构建结果。`evidence/` 追加每次验证原件，`evidence.json` 只指向最新一次登记；旧失败留在原处。`candidates.json` 是当前候选索引，不覆盖旧候选。

## 同版本修补

先查看原候选，为修补另开决策和任务。在决策头部保留相同 `fixed_in`，补上以下两行，再按正常对齐、开发、提交与独立审阅流程处理：

```text
repair_of: 原候选的完整64位标识
repair_reason: 本次发现了什么问题，为什么需要重新准备包
```

两份包与锁文件的版本必须一致；更新说明也要包含本次修补。版本须等于当前 main；版本更低时拒绝，真正的新发行仍使用更高版本且不能携带修补字段。入口验证原候选仍有效、其源码在当前 main 中，并核对 GitHub 标签、所有同版本发行（包括草稿）及 npm 两包状态。查询失败不是“未发布”。

提交修补时，原候选记下修补任务与提交，停止发布原候选。合入后建立下一候选，重新构建、审阅对应改动并重新做隔离验收；旧授权、旧验收不能迁用。该修补标记没有自动撤销入口：若放弃修补，先核对原因与后续决策，不能删除标记恢复旧发布。

仅构建工具变化而源码不变时，可以显式运行 `candidate --version X --id 原候选 --rebuild --reason 原因`。构建输入没有变化时沿用原候选；已被取代的旧输入不会重新成为当前候选。主分支前进后仍需先核对源码，不支持任意历史提交发行。

## 发布前证据与授权

决策可增加 `## 发布前待办`，每项写一行 `- 具体事项`。独立审阅另外返回 `release_requirements`，逐项引用源码或检查证据。它只列必须在公开前完成的事项；普通维护建议仍是建议。旧审阅没有这个字段时，候选增加一项人工核对原决策、审阅和 Issue 的待办。

从这次包制作独立验收目录，完成安装、合成对话、下载失败恢复、更新和重启读回。测试包标识同时包含候选及实际包内容；每次候选重新制作目录，不使用前一候选的下载状态。步骤见 [隔离演练](rehearsal/README.md)。

用以下结构登记本次真实结果。候选、源码、包校验值和待办标识从查询结果与 `release.json` 读取。没有待办时 `requirements` 为 `{}`。每项结论只能按事实写 `pass`、`fail` 或 `unconfirmed`；证据应指向可回查的本机材料，不能编造实际体验。

```json
{
  "candidate": "完整候选标识",
  "source": "源码提交",
  "packages": {
    "@arcfold/dsh": "核心包sha256",
    "@arcfold/dsh-method-ui": "界面包sha256"
  },
  "requirements": {
    "查询返回的待办标识": {"status": "pass", "evidence": "处理记录的位置"}
  },
  "isolated": "本次隔离验收result.json的路径"
}
```

```sh
./Arcfold-DSH-Development candidate --version X --id 候选 --evidence 证据文件
```

登记时把验收原文复制到这次证据中，并记录登记者与时间；以后改动原验收文件不会改变已登记的结论。缺项、不属于这份源码或两份包、验收不通过，均不能公开发行。本机记录用于防止误用证据，不是身份认证或真实体验的自动证明。

待办全部通过后才开发布授权单，正文说明 GitHub 和 npm 哪些实际动作已获授权，`binds` 至少包含 `repo`、`version`、`candidate`、`packages`，包映射与上例相同。不能用只绑定版本号的旧授权替代。登记开发者原话后：

```sh
./Arcfold-DSH-Development release --version X --candidate 候选 --finalize --approval A编号
```

这一步重新核对 main、证据、未答决定单、授权和远端，然后创建标签、上传原包及回执、公开 GitHub 发行。若提供 `--isolated-receipt`，它必须与已登记原文一致。

真实 npm 上传继续按已批准的现有操作执行；以下命令只登记准备状态与核对结果，不运行 `npm publish`：

```sh
./Arcfold-DSH-Development candidate --version X --id 候选 --begin-npm --approval A编号
# 按授权上传本候选原包后核对：
./Arcfold-DSH-Development candidate --version X --id 候选 --check-npm
```

`--begin-npm` 再次检查证据、源码和授权；上一操作结果未知时必须先核对。只上架一份包时显示 `partial`，仅能继续原候选的另一份包。两份 npm 内容与本候选一致才记录 `published`。

## 已写入与结果未知

只要发现同版本标签、GitHub 草稿或公开发行、任一 npm 包，就不允许同版本换内容。已观察到的对外记录即使后来删除，仍保留锁定。远端源码、资产校验值或 npm 内容不同，停止核对，不覆盖。

写入前的本机记录保留操作尝试。结果未知时先查 GitHub/npm 和原请求；单次查询没看到记录不足以证明从未写入。只有确认该尝试没有写入后，才提交 `candidate --version X --reconcile-no-write 核对文件`。文件包含 `outcome: "no_write"`、人工核对的 `evidence`，以及 `journals`（该版本全部写入记录相对路径到当前文件 sha256 的映射）。入口保存原记录全文并再查远端；确认发生过的写入不能解除锁定。后一次尝试有独立身份，不会套用前一次的“未写入”结论。

同机写入沿用全局入口锁，并对每个版本加锁。不能同时让旧入口与新入口交替执行发布。外部直接写入不受本机锁保护，远端冲突会停止；跨机器协调不在本次范围。

## 旧记录

`candidate --version X --import-legacy` 为原 `merges/X.json` 与 `releases/X/` 建索引，保留原文件和原包；只读查询不会自动迁移。资料缺失或对应不上时明确待核对。未构建的旧候选须显式 `--rebuild` 转为新候选。

已有 GitHub 草稿可以在补齐本候选证据和绑定授权后，继续上传及公开原包。接续前核对原标签、草稿与附件，复制旧写入记录到候选目录作为恢复依据，原记录保持不变。旧写入结果未查清时仍停止；这条接续路径不允许同版本修补。
